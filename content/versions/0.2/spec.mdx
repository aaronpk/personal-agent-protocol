# Personal Agent Protocol

## 1. Introduction {#intro}

Personal Agent Protocol (Poppy for short <PronounceButton src="/poppy.wav" label="Play pronunciation of Poppy" />)
defines how a Personal Agent, acting for one User, works with a Company on that User's behalf. It
covers many parts of that interaction, beyond the agent-to-agent conversations that other agent
protocols focus on:

1. **Discovery:** a standard way for the Personal Agent to find everything it needs to work with a
   Company.
2. **Sessions and authorization:** how the agent identifies itself to the Company as an OAuth
   client, how the Company recognizes each User through a pairwise identifier, and how Users
   authorize the agent to use their accounts.
3. **Web browsing:** how the Personal Agent browses the Company's website in the same Session.
4. **APIs:** how the Personal Agent uses the Company's APIs, which can be more efficient than web
   browsing.
5. **Conversations:** how the Personal Agent starts a conversation with the Company Agent, and how
   either side can bring in a person: the User on the Personal Agent's side, or a person at the
   Company.
6. **Extensions:** how Companies and Personal Agents add capabilities beyond this specification,
   described on the [Extensions page](/docs/extensions).

**A profile of AIMS.** This specification is a narrow profile of the AI Identity Management System
framework ([draft-ietf-wimse-aims](https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/)) for
one deployment: a Personal Agent acting for one User, at Companies it has no prior relationship
with. AIMS describes how existing OAuth and WIMSE standards apply to AI agents. This profile picks
the parts that deployment needs and makes the choices AIMS leaves open:

| AIMS                                  | This profile                                                                                                                                                                                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Agent Identifier (§6)                 | The Personal Agent's `client_id`, an HTTPS URL that serves its Client ID Metadata Document (4.1, AIMS §10.10.3). |
| Agent Credentials (§7)                | Keys published at the client's `jwks_uri`, and a separate, unpublished DPoP key for each User (4.1, 4.3).                                                                                                                         |
| Agent Authentication (§9)             | `private_key_jwt` client authentication at the token endpoint (4.1).                                                                                                              |
| User Delegates Authorization (§10.4.1) | The authorization code grant with PKCE, when the User authorizes access to their account (4.4, 4.5), or the device authorization grant where it can't be used (4.6).                                                                                                                              |
| Agent Obtains Own Authorization (§10.4.2) | The JWT authorization grant, which starts a pseudonymous Session with no account access (4.2).                                                                                                                                |
| Discovery (§10.10)                    | Authorization server metadata, protected resource metadata, and Client ID Metadata Documents, found through `poppy.json` (section 3).                                                                                               |
| Human in the Loop (§10.7)             | The [Operations extension](/docs/extensions/operations).                                                                                                                                                                             |
| Security best practices (§10.4.4)     | The OAuth 2.0 Security Best Current Practice ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)) applies in full.                                                                                                                 |

What this profile adds is application protocol: discovery through `poppy.json`, Sessions that tie
web browsing, APIs, and conversations together, and the conversation protocol. The few OAuth
extensions it needs are listed in 9.5.

This is draft version 0.2. Any part of it can change before a stable version, including in ways that
aren't backward compatible. Areas it doesn't cover yet are listed in [Path to
1.0](/docs/path-to-1#open-topics).

The examples use `example.com` for the Company and `agent.example` for the Personal Agent. Tokens,
keys, and codes in the examples are shortened placeholders, not real values.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are used as described in BCP 14 ([RFC
2119](https://www.rfc-editor.org/rfc/rfc2119), [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174))
when they appear in capitals, as shown here.

| Term                           | Meaning                                                                                                                                                                                                                                                  |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Parties**                    |                                                                                                                                                                                                                                                          |
| User                           | The person a Personal Agent acts for. Once they authorize access to their account, the OAuth resource owner.                                                                                                                                            |
| Personal Agent                 | Software acting for the User. It is an OAuth client, and the Agent in AIMS terms (4.1).                                                                                                                                                                  |
| Company                        | An entity that implements the protocol so Personal Agents can work with it. It runs an OAuth authorization server and the resource servers it protects: its APIs, MCP servers, and Company Agent.                                                       |
| **Discovery**                  |                                                                                                                                                                                                                                                          |
| `poppy.json`                   | The JSON document a Company publishes at `/.well-known/poppy.json` to tell Personal Agents its OAuth issuer, and which APIs and Company Agent it offers (section 3).                                                                                     |
| **Sessions and authorization** |                                                                                                                                                                                                                                                          |
| Pairwise subject identifier    | The `sub` a Personal Agent asserts for one User at one Company. It is stable, so the Company recognizes the User across Sessions before they authorize any account access. It is opaque and different at each Company, so Companies can't match Users with each other (4.2). |
| Session                        | One User's activity at one Company through one Personal Agent, across web browsing, APIs, and conversations. It is this protocol's own construct, not the authorization server's login session. A Personal Agent can have several Sessions for the same User (section 4). |
| Pseudonymous Session           | A Session with no account access. Its access tokens have no scopes (4.2).                                                                                                                                                                                |
| Authorized Session             | A Session the User has authorized to use one Company account, through a user authorization grant. Its access tokens carry the scopes the User granted, such as `poppy:read` (4.4).                                                                       |
| Access token                   | A short-lived OAuth access token for a Session, bound to the Personal Agent's DPoP key and used at the Company's APIs and conversations (4.2, 4.3).                                                                                                     |
| Refresh token                  | The long-lived OAuth refresh token from user authorization, which lets the Personal Agent get access tokens for authorized Sessions later without asking the User again. It is used only at the Company's token and revocation endpoints (4.7).         |
| DPoP proof                     | A signed JWT the Personal Agent sends with each request to show it holds the key its access token is bound to ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449), 4.3).                                                                                 |
| **Conversations**              |                                                                                                                                                                                                                                                          |
| Company Agent                  | A Company's own agent, reached through a supported conversation protocol.                                                                                                                                                                                |
| Direct Conversation            | A new conversation, linked to an earlier one, in which the User talks with the Company through the Personal Agent's interface (7.10).                                                                                                                    |
| Conversation ID                | Identifies one conversation, in the URL of each request about it. A conversation belongs to one Personal Agent and one User or account (7.2).                                                                                                            |

## 3. Discovery {#discovery}

A Company MUST publish its `poppy.json` document at `https://{domain}/.well-known/poppy.json` over
HTTPS, where `{domain}` is the Company's domain or a subdomain it controls.

The well-known URL MAY redirect, for example from `www.example.com` to `example.com`. Personal
Agents MUST follow redirects, and every redirect MUST be to an HTTPS URL. Personal Agents SHOULD
cache the document according to its HTTP caching headers.

**Which Company a document speaks for.** A `poppy.json` speaks for the host that serves it, after
any redirects, so a Company that uses a provider has the provider serve it on the Company's own
domain. The document names the Company's OAuth issuer in `auth.issuer`, and the issuer identifies
the Company (3.2). The issuer confirms the link from its side by listing, in its metadata, the
domains whose documents name it. Before using a document, the Personal Agent checks both directions:

1. `organization.domain` is the host that served the document (3.1). This stops a document copied
   to another domain from speaking for the Company.
2. The issuer's metadata has the same `issuer`, and its `poppy_domains` lists `organization.domain`
   (3.2). This stops a domain from claiming another Company's issuer and receiving its tokens.

**HTTPS.** Every URL this protocol defines or exchanges MUST be an HTTPS URL: in `poppy.json`, in
authorization server and protected resource metadata, in client metadata documents (4.1), in
extensions, and in assertions, proofs, and responses. Personal Agents MUST NOT use a URL from a
Company that has another scheme, and Companies MUST reject one from a Personal Agent. This doesn't
cover the pages of a Company's website, which Personal Agents browse as any visitor would (section
5).

**Redirects and addresses.** Outside discovery, a redirect never carries the protocol's secrets. If
the token or revocation endpoint, an API, or a conversation, feedback, or extension endpoint answers
with a redirect, the Personal Agent MUST NOT send a token, DPoP proof, or assertion to the new URL.
Personal Agents and Companies MUST NOT connect to a loopback, private, or link-local address for a
URL the other party gave them, unless they were configured to on purpose. Otherwise a Company could
aim Personal Agents at another Company's servers or at internal ones.

An example document:

```json label="poppy.json, published by the Company"
{
  "protocol_version": "0.2",
  "organization": {
    "name": "Example Company",
    "domain": "example.com"
  },
  "auth": {
    "issuer": "https://auth.example.com",
    "custom_scopes": {
      "addresses": "Manage saved shipping addresses"
    }
  },
  "agent": {
    "protocols": [
      {
        "type": "poppy",
        "endpoint": "https://api.example.com/poppy/conversations"
      }
    ]
  },
  "web": {
    "browser_session_endpoint": "https://example.com/poppy/browser-session"
  },
  "feedback": {
    "endpoint": "https://api.example.com/poppy/feedback"
  },
  "apis": [
    {
      "type": "openapi",
      "url": "https://api.example.com/openapi.json",
      "description": "Orders, returns, and exchanges"
    },
    {
      "type": "mcp",
      "url": "https://mcp.example.com/mcp",
      "description": "Product search and sizing"
    }
  ]
}
```

### 3.2 OAuth server {#oauth-server}

A Company is identified by its `auth.issuer`. Several domains MAY name the same issuer, such as a
Company with a domain for each country, and they are then one Company: the same subject identifiers
(4.2), Sessions, and refresh tokens apply to all of them. Their documents MUST have the same `auth`,
which describes the issuer. Other fields MAY differ by domain, such as the APIs or the website, and
the Personal Agent uses the document of the domain it is working with.

An issuer MUST represent exactly one Company. A provider that hosts several Companies MUST give each
its own issuer, such as `https://auth.provider.example/shop-a`, even when they share servers.
Otherwise the Companies would be one Company under this protocol: Personal Agents would send each of
them the same subject identifiers, and a refresh token from one would be valid at the others.

The issuer MUST publish OAuth Authorization Server Metadata ([RFC
8414](https://www.rfc-editor.org/rfc/rfc8414)), and `poppy_domains` in it MUST list every domain
whose `poppy.json` names the issuer. The metadata is at the URL RFC 8414 (section 3.1) defines,
which puts `/.well-known/oauth-authorization-server` between the issuer's host and its path, if it
has one, such as `https://auth.provider.example/.well-known/oauth-authorization-server/shop-a`.
Before using a Company's `poppy.json`, the Personal Agent fetches the metadata and MUST check that
its `issuer` exactly matches `auth.issuer`, character for character. It MUST also check that
`poppy_domains` includes `organization.domain`, comparing domains ignoring case. Otherwise any
domain could claim another Company's issuer and receive its tokens.

```json label="GET https://auth.example.com/.well-known/oauth-authorization-server"
{
  "issuer": "https://auth.example.com",
  "token_endpoint": "https://auth.example.com/oauth/token",
  "revocation_endpoint": "https://auth.example.com/oauth/revoke",
  "authorization_endpoint": "https://auth.example.com/oauth/authorize",
  "device_authorization_endpoint": "https://auth.example.com/oauth/device",
  "grant_types_supported": [
    "urn:ietf:params:oauth:grant-type:jwt-bearer",
    "authorization_code",
    "urn:ietf:params:oauth:grant-type:device_code",
    "refresh_token"
  ],
  "scopes_supported": ["poppy:read", "poppy:write", "addresses"],
  "token_endpoint_auth_methods_supported": ["private_key_jwt"],
  "token_endpoint_auth_signing_alg_values_supported": ["ES256"],
  "code_challenge_methods_supported": ["S256"],
  "authorization_response_iss_parameter_supported": true,
  "client_id_metadata_document_supported": true,
  "dpop_signing_alg_values_supported": ["ES256", "RS256"],
  "poppy_domains": ["example.com", "example.co.uk"]
}
```

The Personal Agent uses these fields of the metadata:

- `issuer` and `poppy_domains`, which it checks against `poppy.json` (above). Required.
- `token_endpoint` issues access and refresh tokens (4.2, 4.7). Required.
- `revocation_endpoint` revokes refresh tokens (4.8). Required.
- `grant_types_supported` MUST include `urn:ietf:params:oauth:grant-type:jwt-bearer` (4.2). A
  Company that supports user authorization (4.4) also lists `authorization_code` and
  `refresh_token`. Required.
- `authorization_endpoint` starts user authorization (4.5). Required if `grant_types_supported`
  includes `authorization_code`.
- `device_authorization_endpoint` starts the device authorization grant (4.6). Required if
  `grant_types_supported` includes `urn:ietf:params:oauth:grant-type:device_code`, which a Company
  lists only if it offers that grant.
- `scopes_supported` lists the scopes user authorization can grant (4.4). Required if
  `grant_types_supported` includes `authorization_code`.
- `token_endpoint_auth_methods_supported` MUST include `private_key_jwt`, and
  `token_endpoint_auth_signing_alg_values_supported` lists the algorithms the Company accepts for
  client assertions (4.1). Required.
- `code_challenge_methods_supported` MUST include `S256`, and
  `authorization_response_iss_parameter_supported` MUST be `true` ([RFC
  9207](https://www.rfc-editor.org/rfc/rfc9207)), so Personal Agents can rely on PKCE and on `iss`
  in the authorization response (4.5). Required if `grant_types_supported` includes
  `authorization_code`.
- `client_id_metadata_document_supported` MUST be `true`, since Personal Agents identify themselves
  with Client ID Metadata Documents (4.1). Required.

Companies MUST accept DPoP proofs (4.3) signed with `ES256`, so every Personal Agent has an
algorithm that works at every Company. A Company MAY list the algorithms it accepts in
`dpop_signing_alg_values_supported`, as [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449) §5.1
defines, and the list MUST then include `ES256`. Personal Agents MUST sign DPoP proofs with `ES256`
or with an algorithm from that list, except at an MCP server, where the list in the server's
protected resource metadata applies (4.3). The field also tells every other OAuth client of the
issuer that it supports DPoP, so a Company whose issuer serves other clients, such as MCP clients
that use Bearer tokens (section 6), can leave it out.

The metadata MAY have other fields, which Personal Agents ignore. Personal Agents SHOULD cache it
according to its HTTP caching headers.

### 3.3 Extensions {#extensions}

Extensions add optional features on top of this protocol, such as
[operations](/docs/extensions/operations). A Company lists the ones it supports in `extensions`:

```json label="Excerpt from poppy.json"
"extensions": {
  "operations": {
    "version": "1",
    "endpoint": "https://api.example.com/poppy/operations"
  }
}
```

- Extensions defined with this protocol have plain names, such as `operations`. Anyone else MUST
  start an extension's name with a domain they control, such as `example.com/gift-wrap`.
- Each entry has a `version`, the extension's major version. Changes that implementations can safely
  ignore keep the version, and incompatible changes get a new one. Each extension defines its other
  fields.
- A Personal Agent lists the extensions it supports the same way, in `extensions` in its client
  metadata document (4.1).
- Personal Agents and Companies MUST ignore extensions they don't support and fields they don't
  recognize, so either side can work with the other under this specification alone.
- A Company MAY refuse a request it handles only with an extension the Personal Agent doesn't list.
  It returns `extension_required` (HTTP 403) with the extension's name in `extension`. At the token
  endpoint and at endpoints this protocol or an extension defines, such as conversations, the error
  is a JSON body, like other errors there. At APIs, it goes in the `WWW-Authenticate` header, like
  the errors in section 6.

```json label="Response body: Company → Personal Agent"
{ "error": "extension_required", "extension": "operations" }
```

## 4. Sessions and authorization {#sessions}

Everything a Personal Agent does at a Company happens in a Session. A Session belongs to one User,
at one Company, through one Personal Agent, and ties that User's activity together across web
browsing, API calls, and conversations, such as a cart or an open conversation. A Personal Agent can
run several Sessions for the same User at once, for example for tasks running in parallel. Companies
MAY limit what a Personal Agent can do in a Session, pseudonymous or authorized.

The protocol uses the two OAuth token types:

| Token         | What it is                                                                                                                                                           | Used at                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Access token  | A short-lived token for one Session, pseudonymous or authorized. It is bound to a DPoP key the Personal Agent holds (4.3).                                          | The Company's APIs and conversations                                            |
| Refresh token | A long-lived token from user authorization. It stands for the User's grant to this Personal Agent to use their account.                                            | Only the Company's token and revocation endpoints, to get access tokens (4.7)   |

A Session starts pseudonymous: the Company knows which Personal Agent is asking and can recognize
the same User over time, but not who the User is. When a task needs the User's account, the User
authorizes the Personal Agent once, and the Personal Agent keeps the refresh token it gets. Later
Sessions use the refresh token to start authorized without asking the User again, until the User
revokes the authorization, disconnects the Personal Agent, or the refresh token expires. Ending a
Session doesn't affect the refresh token.

The steps, in the order they usually happen:

| Step                          | Request                                                 | Result                                                               |
| ----------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------- |
| Start a Session (4.2)         | `token_endpoint` with the JWT authorization grant       | A new pseudonymous Session and an access token for it                |
| Renew an access token (4.2)   | The same, with `session_id`                             | A new access token for the same pseudonymous Session                 |
| Authorize (4.4–4.6)           | The authorization code grant, or the device grant       | A refresh token, and an access token for the now authorized Session  |
| Use the refresh token (4.7)   | `token_endpoint` with the refresh token                 | An access token for a new or existing authorized Session             |
| Revoke (4.8)                  | `revocation_endpoint` with the refresh token            | The grant is revoked, and Sessions continue pseudonymous             |

The endpoints come from the Company's authorization server metadata (3.2). This section profiles
OAuth 2.0 ([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749)) with the JWT authorization grant
and client authentication ([RFC 7523](https://www.rfc-editor.org/rfc/rfc7523)), PKCE ([RFC
7636](https://www.rfc-editor.org/rfc/rfc7636)), the device authorization grant ([RFC
8628](https://www.rfc-editor.org/rfc/rfc8628)) for Companies that offer it, DPoP ([RFC
9449](https://www.rfc-editor.org/rfc/rfc9449)), resource indicators ([RFC
8707](https://www.rfc-editor.org/rfc/rfc8707)), and token revocation ([RFC
7009](https://www.rfc-editor.org/rfc/rfc7009)), and follows the OAuth 2.0 Security Best Current
Practice ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)). On top of them it adds the
`session_id` parameter, a subject that the Personal Agent asserts rather than the Company, and the
rules in this section. These additions aren't registered OAuth extensions yet, and 9.5 lists them.
A Company can use an existing authorization server that supports them, or put a gateway in front of
one.

### 4.1 Agent identity {#agent-identity}

A Personal Agent's `client_id` MUST be an HTTPS URL that returns its metadata document. Companies
fetch it to learn who the Personal Agent is, to get the keys it signs with, and to check where the
authorization code grant may return the User. This follows the [OAuth Client ID Metadata
Document](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/) draft
that MCP also uses, which AIMS §10.10.3 describes for clients with no prior registration.

```json label="Client metadata document, published by the Personal Agent"
{
  "client_id": "https://agent.example/agent.json",
  "client_name": "Example Agent",
  "logo_uri": "https://agent.example/logo.png",
  "jwks_uri": "https://agent.example/jwks.json",
  "redirect_uris": ["https://agent.example/oauth/callback"],
  "token_endpoint_auth_method": "private_key_jwt",
  "extensions": {
    "operations": { "version": "1" }
  }
}
```

- `client_id` MUST equal the URL the document was fetched from.
- `jwks_uri` and every entry in `redirect_uris` MUST be HTTPS URLs on the same domain as
  `client_id`. The key set contains only public keys.
- `redirect_uris` lists where the authorization code grant may send the User back to (4.5).
- `extensions` lists the extensions the Personal Agent supports, keyed by name, each with its
  `version` (3.3). It is optional.
- The Personal Agent authenticates at the token endpoint with a client assertion signed by a key
  from `jwks_uri` (`private_key_jwt`, [RFC 7523](https://www.rfc-editor.org/rfc/rfc7523)). The same
  keys sign its JWT authorization grant assertions (4.2). Its DPoP keys (4.3) are separate and
  aren't published.
- The client assertion's `aud` MUST be the Company's `auth.issuer`, as a single string. Companies
  MUST reject a client assertion with any other `aud`, compared character for character, including
  their token endpoint URL. This follows
  [draft-ietf-oauth-rfc7523bis](https://datatracker.ietf.org/doc/draft-ietf-oauth-rfc7523bis/). The
  endpoints in a Company's metadata aren't checked (3.2), so an `aud` set to an endpoint could name
  another Company's endpoint, and that Company would accept the assertion.
- The client assertion has `iat`, `exp`, and `jti` with the same rules as the grant assertion
  (4.2).

Companies MAY require Personal Agents to register ahead of time. How registration works is outside
this specification. A Company that requires registration rejects an unregistered Personal Agent with
the OAuth `invalid_client` error (HTTP 401) when it starts a Session.

Companies MAY keep allowlists or blocklists of Personal Agents by `client_id`, and MAY revoke a
`client_id` that misuses the protocol. Companies MAY rate-limit Session creation by `client_id`. A
Company that doesn't require registration MAY also limit how many new `client_id` values it accepts.

### 4.2 Starting a Session {#starting-sessions}

The Personal Agent MUST give each of its Users a pairwise subject identifier for each Company, where
a Company is identified by its `auth.issuer` (3.2). It is the `sub` of the Personal Agent's
assertions. The identifier is stable, so the Company sees the same User across Sessions. It is
opaque and different for each Company, so Companies can't match Users with each other. Because the
identifier is scoped by issuer, this depends on each Company having its own issuer (3.2). It MUST
NOT contain or be derived from personal information, such as an email address, phone number, or
name, even with a keyed hash.

A Personal Agent MAY instead give a User a new subject identifier for each anonymous browsing
session, like a private browser window. The Company sees a new User each time. The Personal Agent
uses the identifier for nothing else, discards it when the browsing session ends, and MUST NOT ask
the User to authorize a Session that uses it (4.4).

The Personal Agent holds the subject identifiers of each of its Users at every Company, and MUST
keep that mapping confidential: it MUST NOT publish it or share it with third parties, other than
service providers that process it on the Personal Agent's behalf.

To start a Session, the Personal Agent requests an access token from the Company's `token_endpoint`
with the JWT authorization grant ([RFC 7523](https://www.rfc-editor.org/rfc/rfc7523) §2.1). The
assertion is a short-lived JWT signed with a key from its `jwks_uri`, naming itself in `iss` and
the User's pairwise subject identifier in `sub`. Unlike most uses of this grant, the client is the
assertion's issuer, and the subject is one the Company hasn't seen before: this is the agent
obtaining its own authorization, as AIMS §10.4.2 describes, scoped to one pseudonymous User. Like
every token request, it also carries the Personal Agent's client assertion (4.1) and a DPoP proof
(4.3). Only a request for a Bearer token for an MCP server can leave the proof out if the MCP server
doesn't support DPoP.

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Ajwt-bearer
&assertion=eyJhbGciOiJFUzI1NiIs…
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

```json label="Assertion claims (JWT payload)"
{
  "iss": "https://agent.example/agent.json",
  "sub": "usr_Q7c1vK",
  "aud": "https://auth.example.com",
  "iat": 1790900000,
  "exp": 1790900060,
  "jti": "V6vJGs2ixBAvGdaQgGaTzg"
}
```

- `iss` is the Personal Agent's `client_id` (4.1).
- `sub` is the pairwise subject identifier for this Company, described above.
- `aud` is the Company's `auth.issuer`, as a single string rather than an array, so the assertion
  can't be used at another Company. As with the client assertion (4.1), the Company MUST reject any
  other `aud`, compared character for character.
- `iat` and `exp` are when the assertion was issued and when it expires, in seconds since 1970 (Unix
  time). `exp` MUST be at most five minutes after `iat`. The assertion is short-lived: one minute in
  this example.
- `jti` is a unique ID for the assertion, with at least 128 random bits. The Company MUST reject a
  `jti` it has already seen from the same `client_id` until the assertion expires, so a copied
  assertion can't be used again.

The Company verifies both assertions against the Personal Agent's `jwks_uri`, checks that the
assertion's `iss` is the authenticated `client_id`, rejects a reused `jti`, and returns a new
Session:

```http label="Response: Company → Personal Agent"
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "eyJhbGciOi…Lm9x",
  "token_type": "DPoP",
  "expires_in": 3600,
  "session_id": "ses_2Lm0"
}
```

- `access_token` is the access token. `token_type` is `DPoP`, or `Bearer` for a token for an MCP
  server that doesn't support DPoP (4.3).
- `expires_in` is the token's lifetime in seconds. The Company chooses the value, and it MUST be
  greater than 0. Access tokens SHOULD last hours, not days.
- `session_id` identifies the Session. It is not a credential.
- `scope` is absent, because a pseudonymous access token has no scopes. A token for an authorized
  Session has `scope` (4.4). Companies MUST leave `scope` out for a pseudonymous Session, and MUST
  include it for an authorized one, even when it equals the requested scope, so the Personal Agent
  can tell them apart. An empty `scope` isn't valid OAuth scope syntax ([RFC 6749, section
  3.3](https://www.rfc-editor.org/rfc/rfc6749#section-3.3)).

**Renewing.** When a pseudonymous Session's access token expires, the Personal Agent sends the same
request with fresh assertions and the `session_id`:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Ajwt-bearer
&assertion=eyJhbGciOiJFUzI1NiIs…
&session_id=ses_2Lm0
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

The Company checks that the Session belongs to the same `client_id` and subject as the assertion,
and returns a new access token for it. An authorized Session is renewed with the refresh token
instead (4.7). The Company decides how long a Session lasts. If it has ended, the Company
returns `invalid_session`, and the Personal Agent starts a new Session.

**Token format.** Access tokens are issued by the Company and are opaque to the Personal Agent.
Personal Agents MUST NOT depend on their contents; everything they need is in the response. A
Company MAY include its own Session credentials in a token so its existing systems can read them. If
it does, it MUST encrypt the token.

Errors use the OAuth error response, with these codes:

| Error                                  | Status | Meaning                                                                                                                               |
| -------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid_client`                       | 401    | The Company doesn't accept this `client_id`: it is unregistered, blocked, or revoked, or its metadata or signature doesn't check out. |
| `invalid_grant`                        | 400    | The assertion or refresh token is missing, expired, reused, revoked, or malformed.                                                    |
| `invalid_session`                      | 400    | The Session has ended, or belongs to a different Personal Agent or User. Start a new Session.                                         |
| `account_mismatch`                     | 400    | The Session is, or was, authorized for a different account than the one requested. Start a new Session (4.4).                       |
| `invalid_dpop_proof`, `use_dpop_nonce` | 400    | The DPoP proof is missing or invalid, or needs a nonce (4.3).                                                                         |
| `extension_required`                   | 403    | The Company requires an extension the Personal Agent doesn't list, named in `extension` (3.3).                                        |
| `rate_limited`                         | 429    | Too many requests for this `client_id`. Retry after the time in the `Retry-After` header.                                             |

### 4.3 Using access tokens {#sending-tokens}

API calls and conversations MUST carry the access token in the `Authorization` header with the
`DPoP` scheme, together with a DPoP proof ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)):

```text label="Request headers: Personal Agent → Company"
Authorization: DPoP eyJhbGciOi…Lm9x
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
```

DPoP in this protocol is meant to match RFC 9449, and anything this section doesn't cover works as
the RFC describes. Where this section and the RFC differ, this section applies. The choices it makes
are:

- Companies MUST accept `ES256`, and listing their algorithms in `dpop_signing_alg_values_supported`
  is optional (3.2).
- Personal Agents MUST support nonces.
- The token endpoint MUST reject a reused `jti`. Elsewhere the check is optional, as in the RFC.
- An MCP server that doesn't support DPoP uses Bearer access tokens, each for that server only.
  Companies MUST require DPoP everywhere else (below).
- Companies don't need to support `dpop_jkt` (RFC 9449 §10).

**Proof of possession.** Access tokens are bound to a key the Personal Agent holds, so a copied
token is useless without it. The Personal Agent MUST use a different key pair for each subject
identifier (4.2), so Companies can't link Users by their keys, and MAY use a new one for each
Session. It keeps the private key to itself and signs a new proof for every request to the token
endpoint and every request that carries an access token. The only exception is a request for a
Bearer token for an MCP server (below) if the MCP server does not support DPoP. Requests that carry neither, such as revocation (4.8)
and device authorization (4.6), don't need a proof. A proof is a JWT with the public key in its header:

```json label="DPoP proof (JWT header and payload)"
{
  "typ": "dpop+jwt",
  "alg": "ES256",
  "jwk": { "kty": "EC", "crv": "P-256", "x": "l8tFrhx-34tV3hRICRDY9zCkDlpBhF42UQUfWVAWBFs", "y": "9VE4jf_Ok_o64zbTTlcuNJajHmt6v9TDVrU0CdvGRDA" }
}
.
{
  "jti": "e1j3V_bKic8-LAEBq7Rw2g",
  "htm": "POST",
  "htu": "https://api.example.com/orders/ord_7Hk2/exchanges",
  "iat": 1790900000,
  "ath": "fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo"
}
```

- `jti` is a unique ID for the proof.
- `htm` and `htu` are the request's HTTP method and URL, without the query or fragment.
- `iat` is when the proof was made.
- `ath` is the SHA-256 hash of the access token sent with it. Proofs sent to the token endpoint
  don't have one.
- `nonce` is included when the Company requires one (below).

When the Company issues an access token, it binds the token to the key in that request's proof. The
Company MUST validate every proof as RFC 9449 §4.3 describes. That means checking that:

- The request has exactly one `DPoP` header, holding a well-formed JWT with the claims above.
- `typ` is `dpop+jwt`, `alg` is an asymmetric algorithm the Company accepts (3.2), never `none`,
  and `jwk` holds a public key and no private key.
- The proof's signature verifies with the key in its header.
- `htm` and `htu` match the request.
- The proof was made within the Company's acceptance window, such as one minute. The Company judges
  this by `iat`, or by when it issued the proof's `nonce`.
- `nonce` matches one the Company issued, if it requires nonces (below).
- On requests with an access token, the key is the one the token is bound to, and `ath` matches the
  token.

**Replayed proofs.** At the token endpoint, the Company MUST reject a proof whose `jti` it has
already accepted within the acceptance window, because a replayed proof there could get a new token.
Everywhere else it accepts DPoP-bound access tokens, such as APIs and conversation endpoints, it MAY
reject a reused `jti`, ideally across all its servers. RFC 9449 (§11.1) doesn't require this check,
because servers behind one endpoint don't always share state. Without it, a copied proof still works
only with the same access token (`ath`), for the same method and URL (`htm` and `htu`), and only
within the acceptance window. A request that changes something then relies on being idempotent, so
a replay doesn't repeat it. Conversation messages already are, through their IDs (7.3).

A Company MAY require proofs to include a nonce it issued, as RFC 9449 describes, so proofs can't be
made in advance. Personal Agents MUST support nonces. A failed check returns `invalid_dpop_proof`,
or `use_dpop_nonce` with the nonce to use in the `DPoP-Nonce` header. The token endpoint returns
them as OAuth errors with HTTP 400 (4.2). APIs and conversation endpoints return HTTP 401 with the
error in the `WWW-Authenticate: DPoP` header (section 6).

**MCP.** MCP authorization uses Bearer tokens, and many MCP servers and clients don't support DPoP.
An MCP server supports DPoP if its protected resource metadata (section 6) lists
`dpop_signing_alg_values_supported`, as [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) §2
defines. To get a token for an MCP server, the Personal Agent sends the request that starts a
Session (4.2, 4.7) or renews its token (4.2, or 4.7 for an authorized Session), and MUST include
`resource` set to the MCP server's `url` from `poppy.json`, as MCP authorization requires. The
Company chooses the token type by that server:

- For an MCP server that supports DPoP, the Company issues a DPoP-bound access token, which the
  Personal Agent uses with proofs, as at any other API. The Company MUST NOT issue a Personal Agent
  a Bearer access token for an MCP server that supports DPoP, so a request without a proof gets
  `invalid_dpop_proof`.
- For an MCP server that doesn't support DPoP, the Company issues a `Bearer` access token, even if
  the request has a proof, and never a DPoP one. The Personal Agent MAY leave the proof out of that
  request.

The Personal Agent MUST use the scheme that `token_type` names. A Session can have a token for each
MCP server and one for its other APIs at the same time. Anyone who copies a Bearer token can use it,
so each one works at only one MCP server. Companies MUST accept a Bearer access token only at the
MCP server whose `url` equals its `resource`, and MUST reject it at every other endpoint, including
other paths on the same host. Everywhere else, Companies MUST require DPoP, and MUST reject a
DPoP-bound access token sent with the `Bearer` scheme (RFC 9449 §7.1). Web browsing doesn't use
access tokens (section 5).

New MCP servers SHOULD support DPoP. Leaving it out is meant for existing MCP servers whose software
can't verify DPoP proofs yet. An MCP server that supports DPoP MUST list `ES256` in its
`dpop_signing_alg_values_supported`, and Personal Agents sign proofs for it with `ES256` or with an
algorithm from that list. It verifies proofs as this section describes, and rejects a DPoP-bound
access token sent with the `Bearer` scheme. It still accepts Bearer tokens from MCP clients that
don't implement this protocol (section 6).

For example, to get a token for an MCP server that doesn't support DPoP, for an authorized Session,
the Personal Agent sends its refresh token (4.7) with `resource` and without a proof:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=pat_8Hk2…Wq1
&session_id=ses_2Lm0
&resource=https%3A%2F%2Fmcp.example.com%2Fmcp
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

```json label="Response: Company → Personal Agent"
{
  "access_token": "eyJhbGciOi…Mc8r",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "poppy:read",
  "session_id": "ses_2Lm0"
}
```

**Narrower tokens.** Any token request MAY include `scope`, to ask for fewer scopes than the Session
has, and `resource` ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)), to ask for a token for one
service. By default, one DPoP-bound access token works at all of a Company's services, except MCP
servers, which accept only tokens issued for them (above). A Company that wants separate tokens for
some services gives those entries a `resource` in its `poppy.json` (section 3), and accepts a token
at such a service only if it was issued for that `resource`.

- Companies MUST accept the token in the `Authorization` header without requiring cookies.
- Personal Agents MUST send an access token on every API and conversation request, and MUST NOT
  leave it out to appear to the Company as a person on their own. Web browsing follows section 5.
- Whenever the Personal Agent gets a new access token for a Session, it MUST use the new token from
  then on.
- Personal Agents MUST NOT send tokens in a URL, and Companies MUST NOT accept them from one.

**Rate limits.** A Company that limits how often a Personal Agent can make requests returns HTTP 429
with a `Retry-After` header when a request goes over the limit, on any of its endpoints, APIs,
conversations, or website. The Personal Agent MUST wait at least that long before sending the
request again. At the token endpoint and at endpoints this protocol or an extension defines, such as
conversations, the body is `{"error": "rate_limited"}`. APIs and the website
keep their own response bodies.

### 4.4 User authorization {#sign-in}

A Session doesn't need user authorization. When a task needs account access and the Personal Agent
has no refresh token that covers it (4.7), the Personal Agent asks the User to authorize access with
the authorization code grant (4.5). This is the grant AIMS §10.4.1 names for a User delegating
authorization to an agent. A Company supports user authorization if its authorization server
metadata lists `authorization_code` in `grant_types_supported` and has an `authorization_endpoint`
(3.2). A Company without them offers only pseudonymous Sessions.

A Company MAY also offer the device authorization grant (4.6). It carries a greater risk of
phishing than the authorization code grant, so Personal Agents SHOULD use the authorization code
grant whenever they can, and use the device authorization grant only when they can't, as 4.6
describes.

The User authenticates and approves access on the Company's own page. A Company can't always verify
that the User did this rather than the Personal Agent, which could complete the page itself.
Personal Agents MUST NOT complete the authorization page for the User. Companies MAY revoke the
`client_id` of a Personal Agent that does (4.1).

**Not in this profile: the User's credentials.** A Personal Agent never needs the User's password
or other credentials for a Company: as AIMS §10.4.1 puts it, OAuth removes the need for the agent to
have them. The OAuth 2.0 Security Best Current Practice says the resource owner password credentials
grant MUST NOT be used ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) §2.4), and an endpoint
that accepts the User's credentials from a Personal Agent is the same grant under another name.
Personal Agents MUST NOT collect a User's credentials for a Company or submit them to the Company,
and Companies MUST NOT offer Personal Agents a way to submit them.

#### Scopes

Scopes say what account access a user authorization grants. The protocol defines two broad scopes:

| Scope         | Account access                                                  |
| ------------- | --------------------------------------------------------------- |
| `poppy:read`  | View account information, such as orders and bookings.          |
| `poppy:write` | Make changes, such as exchanging an item or updating a booking. |

- The scopes are independent: request `poppy:read poppy:write` when both are needed. Companies
  decide which operations require each scope and enforce them across web browsing, APIs, and actions
  performed by the Company Agent.
- The authorization server lists the scopes it can grant in `scopes_supported` (3.2). Companies MAY
  define their own scopes, such as `addresses`, and describe each one in `auth.custom_scopes`
  (3.1). Names starting with `poppy:` are reserved for this protocol, so a Company's existing OAuth
  scopes can't clash with them.
- A Company MAY leave out `poppy:read` and `poppy:write` and offer only its own, narrower scopes, if
  broad access doesn't meet its security needs. The Personal Agent then requests the scopes the task
  needs from those in `scopes_supported`. Personal Agents SHOULD request only the scopes the task
  needs (AIMS §10.9).
- The Company MUST NOT grant scopes beyond those requested.
- Each authorization request MUST include `scope` as a space-separated string, following [OAuth
  scope syntax](https://www.rfc-editor.org/rfc/rfc6749#section-3.3). Missing or unknown scopes are
  rejected with `invalid_scope`.
- If a task needs more access than the refresh token allows, the Personal Agent asks the User to
  authorize again, requesting all the scopes it needs. The new refresh token replaces the old one,
  which the Personal Agent SHOULD revoke (4.8). A pending or failed authorization leaves existing
  tokens unchanged.

User authorization ends with the Company returning a refresh token, and an access token for the
current Session. The User may have approved fewer scopes than requested, so the Personal Agent
checks `scope` before continuing.

```json label="Response: Company → Personal Agent"
{
  "access_token": "eyJhbGciOi…Qp4w",
  "token_type": "DPoP",
  "expires_in": 3600,
  "refresh_token": "pat_8Hk2…Wq1",
  "refresh_token_expires_in": 2592000,
  "scope": "poppy:read poppy:write",
  "session_id": "ses_2Lm0"
}
```

- `refresh_token` is the refresh token (4.7).
- `refresh_token_expires_in` is the refresh token's lifetime in seconds, if the Company sets one.
  After it, the User authorizes again.
- `scope` lists the scopes granted. It is always present for an authorized Session (4.2).

#### How authorization is remembered

The Company keeps a record for each refresh token: the `client_id`, the subject, the account, the
granted scopes, and when it expires. It also keeps a record for each Session: the `client_id`, the
subject, and the account the Session is authorized for, if any.

A Session is authorized for at most one account. Once it has been, it can't switch to another, even
after the authorization is revoked (4.8): the Company returns `account_mismatch`, and the Personal
Agent starts a new Session. If the User authorizes a different account than the Session's, the code
exchange or device grant returns `account_mismatch` and issues no tokens. The User then authorizes
again in a new Session. A User with two accounts at the same Company, such as a personal and a
business account, has a refresh token for each and uses separate Sessions for them.

Each access token reflects the Session as it was when the token was issued. Several tasks can share
one Session, so one may still hold a pseudonymous token after another task got the Session
authorized. A request with that token is handled as pseudonymous, and an account action fails with
`insufficient_scope` (section 6). Before asking the User to authorize, the Personal Agent SHOULD
check whether it already holds a refresh token that covers the task (4.7).

### 4.5 Authorization code grant {#direct-sign-in}

User authorization is the OAuth 2.0 authorization code grant with PKCE ([RFC
6749](https://www.rfc-editor.org/rfc/rfc6749), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)).
It adds one thing: the Personal Agent sends `session_id` when it exchanges the code, so the Company
knows which Session to authorize. The Company's authorization server metadata gives the
`authorization_endpoint` (3.2).

**1. Send the User to the Company.** The Personal Agent creates a random `state` and a PKCE code
verifier, then opens the authorization URL in the User's browser, for example in a new tab, a popup,
or a link sent to the User's phone:

```text label="Authorization URL, opened in the User's browser"
https://auth.example.com/oauth/authorize
  ?response_type=code
  &client_id=https%3A%2F%2Fagent.example%2Fagent.json
  &redirect_uri=https%3A%2F%2Fagent.example%2Foauth%2Fcallback
  &scope=poppy%3Aread%20poppy%3Awrite
  &state=Xq81vR
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256
```

When the User opens the URL on a different device from the Personal Agent, the flow is a
cross-device flow, and Companies SHOULD apply the mitigations in [RFC
10027](https://www.rfc-editor.org/rfc/rfc10027).

**2. The User authenticates and approves.** The Company's page shows which Personal Agent is asking,
using the name and logo from its metadata document. The User authenticates however the Company
allows, such as a passkey, a password, or a provider like Google or Apple. Companies SHOULD offer a
phishing-resistant method, such as a passkey (AIMS §10.4.1). The page shows the requested scopes and
lets the User approve some or all of them, or decline.

**3. The Company sends the User back.** The Company redirects the browser to `redirect_uri` with a
one-time `code`, the same `state`, and its `auth.issuer` in `iss` ([RFC
9207](https://www.rfc-editor.org/rfc/rfc9207)). `redirect_uri` MUST exactly match an entry in the
Personal Agent's `redirect_uris` (4.1). If the User declines, the redirect carries
`error=access_denied` and `iss` instead.

**4. The Personal Agent exchanges the code.** The Personal Agent checks `state`, and MUST check that
`iss` exactly matches the `auth.issuer` of the Company it started the authorization with. This stops
a response from another Company's authorization being swapped in. It then sends the code to the
`token_endpoint` with its client assertion, a DPoP proof, and the `session_id`:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fagent.example%2Foauth%2Fcallback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
&session_id=ses_2Lm0
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

The Company verifies the code, the verifier, and the client assertion, and checks that the Session
belongs to the same `client_id`. It returns a refresh token and an access token for that Session, as
shown in 4.4. Errors follow OAuth 2.0, such as `invalid_grant` for an expired or reused code.

### 4.6 Device authorization grant {#device-sign-in}

The OAuth 2.0 device authorization grant ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628)) lets
the User authorize on a different device from the Personal Agent. The Personal Agent shows the User
a link and a short code, and the User authenticates and approves access on the Company's page on
whatever device they like, such as their phone. It is for Personal Agents that can't receive a
redirect from the authorization code grant (4.5), and for Companies that already offer the grant. A
Company that offers it lists `urn:ietf:params:oauth:grant-type:device_code` in
`grant_types_supported` and gives the `device_authorization_endpoint` in its authorization server
metadata (3.2).

#### Security considerations

The device authorization grant is a cross-device flow, and Companies that offer it and Personal
Agents that use it MUST follow the best practices for cross-device flows in [RFC
10027](https://www.rfc-editor.org/rfc/rfc10027) (BCP 247) §2:

- A Company MUST assess the risk before offering the grant, and SHOULD NOT offer it if the risk
  can't be mitigated enough. RFC 10027 §6.2.1.5 says to use the grant only when no other
  cross-device protocol is viable, and to avoid it for sensitive, high-value, or business-critical
  resources. A Company SHOULD limit the scopes the grant can grant to those whose loss the User and
  Company could recover from (§6.1.9), for example `poppy:read` without `poppy:write`, and MUST
  NOT grant scopes beyond those requested.
- A Company MUST select mitigations from RFC 10027 §6.1 that address its assessment, including at
  least short-lived user codes (§6.1.2), user codes that can be used only once (§6.1.3), rate
  limits (§6.1.11), and a consent page that tells the User who started the request and makes
  declining as easy as approving (§6.1.14). Access tokens are already short-lived and DPoP-bound
  (§6.1.10, §6.1.12).
- A Personal Agent MUST NOT use the device authorization grant when it can use the authorization
  code grant, including whenever the User can open the authorization URL on the device they are
  using to talk to the Personal Agent. RFC 10027 §6.2.1.5 says not to use the grant on the same
  device.

#### Phishing

The device authorization grant is much easier to use for phishing than the authorization code
grant, and Companies and Personal Agents need to treat it that way.

In the authorization code grant, the Company sends the code to the `redirect_uri` registered by the
client that started the request, and PKCE ties the code to that client (4.5). In the device
authorization grant, nothing ties the person who approves the request to the client that started
it: whoever holds the `device_code` gets the tokens. An attacker can start a request at a Company,
then get the User to open the link and enter the code with a pretext sent by email, by message, or
on a web page, such as "enter this code to verify your account." The User sees the Company's real
page, signs in for real, and approves, and the attacker receives a refresh token for the User's
account. This is the exploit RFC 10027 §4.1.1 describes, and it has been used in device code
phishing campaigns against large identity providers. Phishing-resistant authentication such as a
passkey doesn't prevent it, since the User does authenticate to the real Company.

This protocol makes the attack easier in three ways:

- Any Personal Agent can use a Company with no prior registration (4.1), so an attacker can start a
  request as a Personal Agent of its own at any Company that offers the grant.
- The User authorizes on a page they reach from a link and code relayed to them, not from a redirect
  they started, so a User who has been taught that their Personal Agent will show them codes to
  enter is primed to enter one from an attacker.
- The Personal Agent shows whatever link and code the Company returns, so a malicious Company could
  pass off another Company's authorization page as its own, and the User would approve access there
  for the Company that asked.

To reduce the risk:

- Before showing the link and code, the Personal Agent MUST check that the link's host is the host
  of `auth.issuer` or a domain in the issuer's `poppy_domains` (3.2), or a subdomain of either, and
  MUST show the Company's `organization.name` and domain with them.
- The Personal Agent MUST show the link and code only to the User it started the request for, and
  only in the conversation where the User asked for the task, and SHOULD tell the User not to enter
  a code that they didn't ask for.
- The Company's page MUST show which Personal Agent is asking, using the name and logo from its
  metadata document, and the requested scopes. It SHOULD tell the User to approve only if they asked
  that Personal Agent to use their account just now, and SHOULD warn that a code from anyone else is
  a phishing attempt (RFC 10027 §6.1.14).
- Opening the link MUST NOT approve the request by itself, even when the link includes the code.
- The Company SHOULD notify the User through a channel it already has with them, such as email,
  when a Personal Agent gains access this way, so the User can revoke it (4.8) if they didn't
  expect it (RFC 10027 §6.1.6).

#### Steps

**1. Start the request.** The Personal Agent sends the scopes it needs, with its client assertion:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/device
Content-Type: application/x-www-form-urlencoded

scope=poppy%3Aread
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

```json label="Response: Company → Personal Agent"
{
  "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
  "user_code": "WDJB-MJHT",
  "verification_uri": "https://auth.example.com/device",
  "verification_uri_complete": "https://auth.example.com/device?user_code=WDJB-MJHT",
  "expires_in": 300,
  "interval": 5
}
```

**2. The User authenticates and approves.** After the checks above, the Personal Agent shows the
User `verification_uri` and `user_code`, or `verification_uri_complete` as a link or QR code. It
keeps `device_code` private (9.2). The User authenticates on the Company's page, as in 4.5, and
approves some or all of the requested scopes, or declines.

**3. The Personal Agent waits.** Every `interval` seconds, the Personal Agent asks the
`token_endpoint` whether the User has finished, with its client assertion, a DPoP proof, and the
`session_id`:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Adevice_code
&device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS
&session_id=ses_2Lm0
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

Until the User finishes, the Company returns `authorization_pending`, or `slow_down` to ask the
Personal Agent to wait longer between requests. Once the User approves, the Company checks that the
Session belongs to the same `client_id` and returns a refresh token and an access token for that
Session, as shown in 4.4. If the User declines, it returns `access_denied`, and if the request runs
past `expires_in`, `expired_token`. The Personal Agent stops asking after either.


### 4.7 Refresh tokens {#account-tokens}

A refresh token lets the Personal Agent get access tokens for authorized Sessions later without
asking the User to authorize again ([RFC 6749, section
6](https://www.rfc-editor.org/rfc/rfc6749#section-6)).

The Personal Agent sends the refresh token to the `token_endpoint` with its client assertion and a
DPoP proof. With `session_id`, it gets an access token for that Session, authorizing it if it was
pseudonymous. Without one, it starts a new Session that is already authorized:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/token
Content-Type: application/x-www-form-urlencoded
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…

grant_type=refresh_token
&refresh_token=pat_8Hk2…Wq1
&session_id=ses_4Tn8
&scope=poppy%3Aread
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

The response has the same fields as in 4.4, without a new `refresh_token` unless the Company rotates
it (below).

- Companies MUST accept a refresh token only at their `token_endpoint` and `revocation_endpoint`,
  and only from the `client_id` it was issued to, authenticated by its client assertion. A copied
  refresh token is useless without the Personal Agent's private key.
- The Session MUST belong to the same `client_id` and subject as the refresh token, and MUST NOT
  have been authorized for a different account, even if it is now pseudonymous (4.4). Otherwise the
  Company returns `invalid_session` or `account_mismatch`.
- `scope` MAY ask for fewer scopes than the refresh token has, for example read-only access for a
  task that only looks things up. It can't ask for more.
- Using a refresh token doesn't extend its lifetime. A Company MAY return a new refresh token in
  `refresh_token`. The Personal Agent then MUST use the new one from then on.
- When the refresh token has expired or been revoked, the Company returns `invalid_grant`. The
  Session continues pseudonymous, and the User authorizes again when a task needs the account.
- Personal Agents MUST store refresh tokens as secrets, and MUST NOT put them in model context,
  conversation messages, logs, or URLs.

### 4.8 Revoking authorization {#sign-out}

Revoking the authorization removes the Personal Agent's access to the User's account. The Personal
Agent revokes its refresh token at the Company's `revocation_endpoint` ([RFC
7009](https://www.rfc-editor.org/rfc/rfc7009)), with its client assertion:

```http label="Request: Personal Agent → Company"
POST https://auth.example.com/oauth/revoke
Content-Type: application/x-www-form-urlencoded

token=pat_8Hk2…Wq1
&token_type_hint=refresh_token
&client_id=https%3A%2F%2Fagent.example%2Fagent.json
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs…
```

The Company revokes the refresh token, and every Session authorized with it becomes pseudonymous.
Usually those Sessions continue, as described below: the Personal Agent renews them with its
assertion (4.2) and gets pseudonymous access tokens. Such a Session can be authorized again only for
the same account (4.4). A Company MAY end the Sessions instead, if its policy is to clear everything
when access is revoked. Renewal then returns `invalid_session`, and the Personal Agent starts a new
Session.

As RFC 7009 §2.1 describes, the Company SHOULD also invalidate the access tokens issued under the
same grant, so the revocation takes effect right away. A Company that can't SHOULD check on each
request whether the Session is still authorized, and one that does neither SHOULD use much shorter
access token lifetimes, such as a few minutes.

An access token expiring isn't a revocation. Work the Company accepted with a valid token, such as a
long-running job, can continue after that token expires. When the account's access is revoked, by
the Personal Agent or by the User disconnecting it, the Company MAY stop work in progress that uses
the account, or let it finish.

To end a Session without revoking the authorization, the Personal Agent stops using it. The refresh
token is unaffected and can start new Sessions.

The User can also disconnect the Personal Agent from the Company's account settings. That revokes
the Personal Agent's refresh tokens for that account, and its Sessions for that account become
pseudonymous. The Personal Agent finds out when a request fails with `invalid_token` or
`insufficient_scope`, or the token endpoint returns `invalid_grant` for the refresh token. It then
continues pseudonymous.

**After revocation.** When a Session continues pseudonymous, after the User revokes the
authorization or disconnects the Personal Agent:

- What doesn't need the account carries on, such as a cart or a conversation that hasn't used the
  account.
- Anything that used the account, such as a conversation (7.11) or an operation ([Operations
  extension](/docs/extensions/operations#ownership)), stays as it is, but the Company answers a
  request on it with a pseudonymous token with `insufficient_scope`. A conversation stays open, so
  the User can authorize again and continue it.
- The Personal Agent SHOULD NOT ask the User to authorize that account again unless the User asks
  for it, even when a request gets `insufficient_scope`.

## 5. Web browsing {#web-browsing}

A Personal Agent can browse the Company's website in the same Session it uses for APIs and
conversations, so the Company sees one Session for the User, pseudonymous or authorized.
The Personal Agent's browser joins the Session by posting a signed browser assertion to the Company,
and the Company sets a cookie of its own for that Session.

This is optional. A Company that supports it lists `web.browser_session_endpoint` in its
`poppy.json` (section 3). When it does, the Personal Agent MUST join its browser to a Session before
browsing the Company's website. On a website without the endpoint, the Personal Agent browses as an
ordinary visitor.

**1. The Personal Agent signs a browser assertion.** It is a JWT signed with a key from the Personal
Agent's `jwks_uri`, like the grant assertion that starts a Session (4.2), with `typ` set to
`poppy-browser+jwt` in its header:

```json label="Browser assertion claims (JWT payload)"
{
  "iss": "https://agent.example/agent.json",
  "sub": "usr_Q7c1vK",
  "aud": "https://example.com/poppy/browser-session",
  "session_id": "ses_2Lm0",
  "return_to": "https://example.com/orders",
  "iat": 1790900000,
  "exp": 1790900060,
  "jti": "Hk29vQ0sPZ1mXa7cR4tLwA"
}
```

- `iss`, `sub`, `iat`, and `jti` are as in 4.2.
- `aud` is the Company's `web.browser_session_endpoint`.
- `session_id` is the Session the browser joins, pseudonymous or authorized.
- `return_to` is the page to open afterward. It MUST be an HTTPS URL on the Company's
  `organization.domain` or one of its subdomains.
- `exp` is no more than 60 seconds after `iat`.

**2. The browser posts it.** The Personal Agent has its browser send the assertion to the endpoint
as a form POST, as a top-level navigation, so the cookie the Company sets lands in that browser. For
example, it loads a page with a form that submits itself. The assertion MUST go in the request body,
never in the URL.

```http label="Request: Personal Agent's browser → Company"
POST https://example.com/poppy/browser-session
Content-Type: application/x-www-form-urlencoded

assertion=eyJ0eXAiOiJwb3BweS1icm93c2VyK2p3dCIsImFsZyI6IkVTMjU2In0…
```

The Personal Agent MUST post browser assertions only from a browser it controls, never from the
User's own browser, which would then be using the Personal Agent's Session.

**3. The Company checks it and sets a cookie.** The Company MUST check that:

- The signature verifies with a key from the `iss` client's `jwks_uri`, and `typ` is
  `poppy-browser+jwt`. A grant assertion isn't accepted here, and a browser assertion isn't
  accepted at the token endpoint.
- `aud` is its endpoint, the assertion hasn't expired, and `exp` is no more than 60 seconds after
  `iat`.
- It hasn't accepted the same `jti` before. It only needs to remember a `jti` until the assertion
  expires.
- The Session is active and belongs to the same `client_id` and User.
- `return_to` is on its own domain.

If every check passes, the Company sets a cookie for the Session and responds with `303 See Other`
to `return_to`. If not, it sets no cookie and returns an error page with HTTP 400.

```http label="Response: Company → Personal Agent's browser"
HTTP/1.1 303 See Other
Location: https://example.com/orders
Set-Cookie: sb_session=Pz81kQ…; Path=/; Secure; HttpOnly; SameSite=Lax
```

**The cookie.** The cookie is the Company's own. The Company chooses its name, value, the hosts it
covers, and its lifetime, and links it to the Session on its servers. The cookie:

- MUST follow the Session's current state: when the Session is authorized or revoked, or its scopes
  change, the website reflects it on the next request.
- MUST NOT outlive the Session.
- MUST be `Secure` and `HttpOnly`, and use `SameSite=Lax` or `None`, not `Strict`. The POST comes
  from a page the Personal Agent created, so with `Strict` the browser wouldn't send the cookie when
  it follows the redirect.

The website applies the Session's scopes, as the Company's APIs do. While the browser carries the
Session's cookie, the Company handles its requests as that Session, pseudonymous or authorized,
whatever other cookies the browser holds from earlier visits.

The Personal Agent MAY post a new browser assertion at any time, for example when the website no
longer recognizes the Session. Each one replaces the cookie the Company set before.

## 6. APIs {#apis}

A Company can list APIs in its `poppy.json` (section 3). Each API's `type` MUST be one of these:

| Type      | `url` points to                                                                                        | Specification                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `openapi` | An OpenAPI 3.0 or 3.1 description of the API.                                                          | [OpenAPI Specification 3.1](https://spec.openapis.org/oas/v3.1.1.html)                        |
| `mcp`     | A remote MCP server endpoint, using the Streamable HTTP transport and MCP version 2025-06-18 or later. | [Model Context Protocol 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18) |

Personal Agents SHOULD skip API types they don't recognize, so later versions can add types. The
protocol leaves each API's schema to that API. Every listed API MUST accept access tokens as
described in 4.3: DPoP for OpenAPI, and for MCP, DPoP if the server supports it and Bearer if it
doesn't.

A listed MCP server MUST accept the Company's access tokens and enforce their scopes. It
MUST accept only tokens issued for its `url` (4.3). MCP clients find where to get a token from the
server's protected resource metadata ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)), and its
`authorization_servers` MUST include `auth.issuer`. An MCP client that doesn't implement this
protocol can then use MCP's own authorization flow, and the Company treats that authorization as
starting a new authorized Session. Such a Session has no pairwise subject identifier, so the rules
in 4.2 don't apply: it belongs to the MCP client and the authorized account. It can't continue
pseudonymous, so it ends when the authorization is revoked or expires.

The Personal Agent calls a Company API the way that API's type describes, with the token in the
`Authorization` header:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/orders/ord_7Hk2/exchanges
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json
Idempotency-Key: 4f1c2e8a-9b7d-4c3e-a5f6-0d8b1e2c3a4f

{ "item_id": "itm_4Qa", "replacement_sku": "stormline-insulated-m" }
```

These errors are returned in the `WWW-Authenticate` header ([RFC
9449](https://www.rfc-editor.org/rfc/rfc9449), or [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750)
for Bearer tokens). An MCP server's 401 responses carry a challenge for each scheme it accepts,
`Bearer` and, if it supports DPoP, `DPoP`, and each challenge includes `resource_metadata` with the
server's protected resource metadata URL ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) §5.1):

| Error                | Status | Meaning                                                                                                                                                                                          |
| -------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `invalid_token`      | 401    | The token is missing or expired. The Personal Agent gets a new one (4.2, 4.7).                                                                                                                   |
| `invalid_dpop_proof` | 401    | The DPoP proof is missing or invalid (4.3).                                                                                                                                                      |
| `use_dpop_nonce`     | 401    | The Company requires a nonce, given in the `DPoP-Nonce` header (4.3). The Personal Agent retries with a new proof that includes it.                                                              |
| `insufficient_scope` | 403    | The token lacks the scopes the request needs, which the response names in the `scope` attribute. A pseudonymous token has no scopes, so this is also the answer to a request that needs the User's account. The Personal Agent uses a refresh token that covers them (4.7), or asks the User to authorize (4.4), and retries, unless the User revoked its access (4.8). |
| `extension_required` | 403    | The request needs an extension the Personal Agent doesn't list, named in the `extension` attribute (3.3). An MCP server returns it only to refuse the Personal Agent entirely, not for one tool. |

Because every token is issued to a known `client_id` and subject, the Company always knows a request
comes from a Personal Agent, which one, and for which User.

```http label="Response: Company → Personal Agent"
HTTP/1.1 403 Forbidden
WWW-Authenticate: DPoP error="insufficient_scope", scope="poppy:read poppy:write"
```

## 7. Conversations {#conversations}

A conversation is how the Personal Agent and the Company talk. The Personal Agent talks with the
Company on the User's behalf, and brings decisions back to the User when needed. Each message says
whether a person or an AI wrote it (7.8).

When the User wants to talk with the Company themselves, or the Company asks for them, the Personal
Agent opens a Direct Conversation (7.10): a new conversation, linked to the first, that the User
sees and takes part in. The User doesn't have to read the exchange between the two agents that came
before it.

### 7.1 Conversation protocols {#conversation-protocols}

A Company lists one or more conversation protocols in `agent.protocols`. Each entry has a `type` and
an `endpoint`. The Personal Agent chooses a protocol it supports and uses that entry's endpoint for
the conversation. It skips unfamiliar types. The currently defined protocol is:

| Type    | Protocol                              | Reference                                                           |
| ------- | ------------------------------------- | ------------------------------------------------------------------- |
| `poppy` | Personal Agent Protocol conversations | The message, event, and streaming format defined in 7.2–7.13 below. |

### 7.2 Requests {#conversation-requests}

Personal Agent Protocol conversations use JSON over HTTPS. Below, `{endpoint}` is the `endpoint` of
the selected `poppy` entry, and `{id}` is a Conversation ID. Every request carries an access token
with a DPoP proof (4.3).

| Request                         | Purpose                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------- |
| `POST {endpoint}`               | Start a conversation with its first message (7.3), or a Direct Conversation (7.10). |
| `POST {endpoint}/{id}/messages` | Send another message (7.3).                                                         |
| `GET {endpoint}/{id}/events`    | Read messages and other events, or stream them (7.5, 7.6).                          |
| `POST {endpoint}/{id}/handoff`  | Ask for a person at the Company (7.9).                                              |
| `POST {endpoint}/{id}/close`    | Close the conversation (7.12).                                                      |

A conversation belongs to the Personal Agent's `client_id` and the subject that started it. Once it
uses the User's account, it belongs to that account instead. Any Session that matches can continue
it, so a conversation can outlast the Session that started it. The Company MUST reject requests from
any other `client_id`, User, or account.

**IDs.** Conversation IDs, message IDs, and event IDs are strings of 1 to 256 characters from the
URL-safe base64 alphabet ([RFC 4648, section 5](https://www.rfc-editor.org/rfc/rfc4648#section-5)):
letters, digits, `-`, and `_`. They SHOULD start with a short prefix for their kind, such as `cnv_`,
`msg_`, or `evt_`. The Company chooses Conversation IDs and event IDs, and the Personal Agent
chooses message IDs for its own messages. Beyond these rules, the side that chooses an ID decides
its format, and the other side MUST NOT depend on it.

### 7.3 Sending messages {#sending-messages}

A new conversation starts with its first message:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{
  "message": {
    "id": "msg_Yq3v8LrT0aWc5NkE",
    "sender": "agent",
    "text": "The jacket from order #1042 isn't warm enough. The user wants to return it.",
    "context": { "locale": "en-US", "time_zone": "America/Los_Angeles", "user_available": true }
  }
}
```

The Company returns the new conversation's ID:

```http label="Response: Company → Personal Agent"
HTTP/1.1 201 Created
Content-Type: application/json

{
  "conversation_id": "cnv_8f3Kd2",
  "status": "working",
  "responder": "agent"
}
```

Later messages go to the conversation's `messages` URL, which returns HTTP 202 with the same fields:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations/cnv_8f3Kd2/messages
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{
  "message": { "id": "msg_Hc72PwZn4eKs1QxB", "sender": "agent", "text": "Does the insulated version come in medium?" }
}
```

**Message IDs.** The Personal Agent chooses each message's `id`, and MUST make it unique for the
User. To retry a message, it sends it again with the same ID. If the Company has already accepted a
message with that ID and the same content, it returns the original response and doesn't add the
message again. Because the ID is unique for the User rather than for one conversation, the Company
can recognize a retried first message and return the conversation it already started. If the content
is different, the Company returns `message_id_conflict`. The Company keeps this check for as long as
it keeps the conversation.

**Replies in the response.** To get the Company's reply in the same request, the Personal Agent adds
the `wait` query parameter to either `POST`, and `cursor` if it has one. The Company accepts the
message, then responds as a read of the conversation's events from that cursor would (7.5), holding
the request for up to `wait` seconds. Without a cursor, it reads from the start of the conversation.
The status code stays 201 or 202:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations/cnv_8f3Kd2/messages?cursor=evt_c2&wait=10
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{
  "message": { "id": "msg_Tb5nRw8Ke2Lp0VsD", "sender": "agent", "text": "Medium, please." }
}
```

### 7.4 Message fields {#message-fields}

| Field     | Req. | Description                                                                                                                                                                                     |
| --------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`      | Yes  | The message's ID, chosen by the Personal Agent and unique for the User (7.3).                                                                                                                   |
| `role`    | No   | `user` or `company`, the side the message came from. The Company sets it when it records the message as an event (7.5). The Personal Agent doesn't send it, and the Company ignores it if sent. |
| `sender`  | Yes  | `agent` if the Personal Agent wrote the message, `human` if the User wrote it (7.8).                                                                                                            |
| `text`    | No   | The message in natural language.                                                                                                                                                                |
| `data`    | No   | A JSON object for structured details that would need markup, like a list or a table, to fit in a sentence. The protocol doesn't define its keys.                                                |
| `context` | No   | Facts about the User's situation, such as `locale`, `time_zone`, and `user_available` (below).                                                                                                  |

A message MUST have at least one of `text`, `data`, or `context`.

Use `text` for the message itself, including simple values like an email address or an order number.
Use `data` for structured details that would otherwise need markup to fit in a sentence. Personal
Agents and Company Agents SHOULD NOT put JSON or other markup in `text`. The Company Agent's replies
use `data` the same way.

For example, choosing seats for a family of six, with their loyalty and security numbers:

```json label="Message: Personal Agent → Company"
{
  "id": "msg_Ns8dXo1Gv6JpUa3C",
  "sender": "agent",
  "text": "The user would like seats together for their family of six on flight SB 482.",
  "data": {
    "travelers": [
      { "name": "Dana Reyes", "seat": "14A", "frequent_flyer": "SB 4821 9930", "known_traveler": "TT7K2M9QX" },
      { "name": "Sam Reyes", "seat": "14B", "frequent_flyer": "SB 4821 9947", "known_traveler": "TT9W4R1LD" },
      { "name": "Ava Reyes", "seat": "14C", "frequent_flyer": "SB 5530 1182" },
      { "name": "Leo Reyes", "seat": "15A" },
      { "name": "Mia Reyes", "seat": "15B" },
      { "name": "Noah Reyes", "seat": "15C" }
    ]
  }
}
```

The Personal Agent decides how much of the User's situation to share, and sharing more up front
saves rounds of back-and-forth.

**Context.** `context` holds facts about the User's situation that affect how the Company replies,
so the Personal Agent doesn't have to write them into the text. The Company gives it to the Company
Agent along with the messages. When a Personal Agent shares one of these facts, it MUST use the
field and format defined here:

- `locale` is a language tag such as `en-US` ([RFC 5646](https://www.rfc-editor.org/rfc/rfc5646)),
  for the language and formatting of replies.
- `time_zone` is an IANA time zone name such as `America/Los_Angeles`, for reading and showing
  times.
- `user_available` is `true` if the User can answer questions right now.

`context` MAY include other fields, such as accessibility needs or preferred units. The Company
Agent interprets them as it sees fit, and a Company MAY ignore them. Details of the request itself
belong in `text` or `data`, not `context`. Personal Agents SHOULD share only what the task needs.

Any message can carry `context`, and fields it leaves out keep their previous values. A message with
only `context` updates it without saying anything else, for example when the User steps away:

```json label="Message: Personal Agent → Company"
{
  "id": "msg_Lw0eFj7Tc2RbVy5H",
  "sender": "agent",
  "context": { "user_available": false }
}
```

Company messages have `id`, `role`, `sender`, `text`, and `data`, with an ID the Company chooses.
Only the Personal Agent sends `context`. Extensions can add fields, such as `operation` in the
[Operations extension](/docs/extensions/operations#binding-conversations).

### 7.5 Reading events {#reading-events}

The Company records each conversation as an ordered list of events: the messages from both sides,
and changes to the conversation. The Personal Agent reads the events after the last cursor it saved:

```http label="Request: Personal Agent → Company"
GET https://api.example.com/poppy/conversations/cnv_8f3Kd2/events?cursor=evt_c1&wait=30
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
```

```json label="Response: Company → Personal Agent"
{
  "conversation_id": "cnv_8f3Kd2",
  "events": [
    {
      "id": "evt_c2",
      "type": "message",
      "created_at": "2026-10-08T19:03:00Z",
      "message": {
        "id": "msg_r2Kq",
        "role": "company",
        "sender": "agent",
        "text": "I can do that. The insulated version would be warmer. Want to exchange instead for $70 more?",
        "data": { "replacement_sku": "stormline-insulated-m", "price_difference": 70 }
      }
    }
  ],
  "cursor": "evt_c2",
  "has_more": false,
  "status": "idle",
  "responder": "agent"
}
```

Every event has an `id`, a `type`, and a `created_at` time ([RFC
3339](https://www.rfc-editor.org/rfc/rfc3339)). The type says which other fields it has:

| Type                             | Fields                                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `message`                        | `message`: a message from either side, as it was sent, with `role` set by the Company to `user` or `company` for the side it came from. Every message the Company accepts is recorded, including one with only `context`. |
| `state`                          | `status` and `responder`, after either one changes. See 7.7 for their values.                                                                                                                                             |
| `authorization`                  | `error` and `scope`: the Company needs the User's account, or more scopes (7.11).                                                                                                                                         |
| `user_requested`                 | `reason`: the Company asks to talk with the User directly (7.10).                                                                                                                                                         |
| `direct_opened`, `direct_closed` | `conversation_id`: a Direct Conversation linked to this one opened or closed (7.10).                                                                                                                                      |

Personal Agents MUST skip event types they don't recognize, so later versions and extensions can add
types.

- `cursor` and `wait` are query parameters, here and on the `POST` requests in 7.3.
- Each event's `id` is also a cursor. Without a `cursor`, the read starts at the beginning of the
  conversation. Cursors are opaque, so the Personal Agent MUST NOT compare or sort them.
- `wait` is a whole number of seconds, 0 or more. The Company holds the request for up to `wait`
  seconds until there is an event to return. It MAY return sooner, or cap `wait`: a larger `wait` is
  held only as long as the cap, not rejected. Without `wait`, it returns right away. A read that
  times out returns an empty `events` list.
- Every successful read MUST include `conversation_id`, `events`, `cursor`, `has_more`, `status`,
  and `responder`, with `events` empty when there are none. `cursor` is the last event returned, or
  the request's cursor if there were none. When `has_more` is `true`, the Personal Agent reads again
  right away.
- The Personal Agent handles events in order and saves the cursor after them. A read after a
  reconnect can return events again, so it skips event IDs it has already handled.
- The Company keeps events for as long as it chooses. A cursor for events it no longer has returns
  `cursor_expired`. The Personal Agent then reads from the beginning and SHOULD tell the User that
  part of the conversation is missing.

### 7.6 Streaming {#streaming}

A Company MAY stream events with server-sent events
([SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html)). The Personal Agent asks for
a stream by sending `Accept: text/event-stream` on a read. A Company that doesn't stream returns
JSON as usual. In a stream, each event has its event ID as the SSE `id` and the same event JSON as
`data`:

```text label="Stream: Company → Personal Agent"
id: evt_c2
data: {"id":"evt_c2","type":"message","created_at":"2026-10-08T19:03:00Z","message":{…}}
```

Changes to `status` and `responder` arrive as `state` events. The Company MAY close a stream at any
time, for example when the access token expires. The Personal Agent reconnects with `Last-Event-ID`
set to the last event it handled, in place of `cursor`. If a request has both, `Last-Event-ID` wins,
because SSE clients add it to the URL the stream was first opened with.

While the Company Agent writes a message, the Company MAY send pieces of its text as `text-delta`
events, with no SSE `id`:

```text label="Stream: Company → Personal Agent"
event: text-delta
data: {"message_id":"msg_r2Kq","text":"I can do that. "}
```

The Personal Agent can show the pieces as they arrive, then replaces them with the complete
`message` event. It MUST NOT act on text from a `text-delta` event. After a reconnect, it drops any
pieces of a message it didn't receive in full.

### 7.7 Status and responder {#status}

| Status    | Meaning                                                                 |
| --------- | ----------------------------------------------------------------------- |
| `working` | The Company is still working. Read again with the cursor.               |
| `idle`    | The Company has no work in progress and is waiting for the User's side. |
| `queued`  | Waiting for a person at the Company to join (7.9).                      |
| `closed`  | The conversation takes no more messages (7.12).                         |

`responder` tells the Personal Agent who is currently handling the Company side of the conversation.
It is independent of `status`:

| Responder | Meaning                                                    |
| --------- | ---------------------------------------------------------- |
| `agent`   | An automated Company Agent is handling the conversation.   |
| `human`   | A live person at the Company is handling the conversation. |

Every successful response to a `POST` or a read MUST include `status` and `responder`. Every change
to either one adds a `state` event with both, even if there is no new text. `human` means a person
has joined. While the conversation is `queued`, `responder` stays `agent`. In a closed conversation,
`responder` is whoever handled it last.

Each Company message MUST also include `sender`, with `agent` or `human`, to identify who wrote it.
This distinguishes earlier automated replies from human replies when both arrive in one response.
The `role` stays `company` in either case.

```json label="Response: Company → Personal Agent"
{
  "conversation_id": "cnv_8f3Kd2",
  "events": [
    {
      "id": "evt_c4",
      "type": "state",
      "created_at": "2026-10-08T19:05:10Z",
      "status": "idle",
      "responder": "human"
    },
    {
      "id": "evt_c5",
      "type": "message",
      "created_at": "2026-10-08T19:05:20Z",
      "message": {
        "id": "msg_t8Vn",
        "role": "company",
        "sender": "human",
        "text": "I've reviewed the exchange. Can you confirm which size the user wants?"
      }
    }
  ],
  "cursor": "evt_c5",
  "has_more": false,
  "status": "idle",
  "responder": "human"
}
```

### 7.8 Human or AI {#human-or-ai}

Both sides say whether a person or an AI is taking part. On the Personal Agent's side, the Personal
Agent MUST set each message's `sender`: `agent` when the Personal Agent wrote it, and `human` only
when it carries the User's own words. A summary, paraphrase, or translation of what the User said is
`agent`. On the Company's side, `responder` and each message's `sender` do the same (7.7).

When the User steps in, the Personal Agent sends their words with `sender: "human"` in the same
conversation:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations/cnv_8f3Kd2/messages
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{
  "message": { "id": "msg_Fz4kQa9Ue1YoBs6R", "sender": "human", "text": "Medium, please." }
}
```

Each side uses this to adapt. When both sides are AI, they can skip greetings and small talk, keep
text short, and put structured details in `data`. When a person is on either side, the other side
writes for that person: plain sentences, a pace they can follow, and details in `text` rather than
only in `data`. In a Direct Conversation, the Company replies as it would to the customer on its own
channels.

### 7.9 Handoff to a person {#handoff}

The Personal Agent asks for a person at the Company with an empty JSON object:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations/cnv_8f3Kd2/handoff
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{}
```

The Company returns HTTP 202 with `status` and `responder`, and the status becomes `queued` while it
finds someone. When a person joins, `responder` becomes `human`. If no one is available, the status
goes back to `idle` with `responder` still `agent`, and the Company Agent says why in a message. The
Company Agent can also hand off to a person on its own. If the conversation is already `queued`, or
a person is already handling it, the Company returns HTTP 202 with the current `status` and
`responder` and changes nothing.

The Personal Agent can keep sending messages while it waits, for example to explain the problem for
the person who joins or to update `user_available`. Closing the conversation cancels a pending
handoff. A person at the Company is held to the same scopes as the Company Agent (7.11).

### 7.10 Direct Conversations {#direct-conversations}

A Direct Conversation lets the User talk with the Company themselves. It is a new conversation,
linked to the one before it, so the User sees only the Direct Conversation, while the Company keeps
the earlier history and can use it. The Personal Agent sends the User's messages as written, with
`sender: "human"` (7.8), and shows the Company's replies to the User.

**Starting one.** The Personal Agent starts a Direct Conversation like any other (7.3), adding
`parent_conversation_id` with the earlier conversation's ID. The Company returns a new Conversation
ID as usual:

```http label="Request: Personal Agent → Company"
POST https://api.example.com/poppy/conversations
Authorization: DPoP eyJhbGciOi…Qp4w
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs…
Content-Type: application/json

{
  "parent_conversation_id": "cnv_8f3Kd2",
  "message": { "id": "msg_Pe6jWm3Kd0RtXc8V", "sender": "human", "text": "Hi, I have a question about the exchange." }
}
```

The parent conversation MUST be open, belong to the same owner (7.2), and not be a Direct
Conversation itself. It can have one open Direct Conversation at a time. Otherwise the Company
returns `conversation_not_found`, `conversation_closed`, or `direct_conversation_open`.

**When the Company asks.** The Company asks to talk with the User by adding a `user_requested` event
to the conversation, with a short `reason`:

```json label="Event: Company → Personal Agent"
{
  "id": "evt_c6",
  "type": "user_requested",
  "created_at": "2026-10-08T19:06:00Z",
  "reason": "A specialist needs to confirm the exchange with the customer."
}
```

The event doesn't change `status` or `responder`.

The Personal Agent asks the User. If they agree, it starts a Direct Conversation as above. If they
decline or aren't available, it says so in the conversation. Only the Personal Agent starts Direct
Conversations, so the User decides when they're brought in.

**The parent conversation meanwhile.** When a Direct Conversation opens, the Company adds a
`direct_opened` event to the parent, with the Direct Conversation's ID in `conversation_id`. While
it is open, the parent can still be read, but messages and handoff requests to the parent return
`direct_conversation_open`, with the Direct Conversation's ID in `conversation_id`. When the Direct
Conversation closes, the Company adds a `direct_closed` event to the parent, and the parent takes
messages again. The Company Agent in the parent knows what was said in the Direct Conversation.
Closing the parent also closes its open Direct Conversation.

### 7.11 Authorization during a conversation {#conversation-sign-in}

With a pseudonymous token, the Company Agent can answer general questions. When the Company Agent
needs the User's account, the Company adds an `authorization` event. It SHOULD also ask in a
message, so a User in a Direct Conversation sees the request:

```json label="Event: Company → Personal Agent"
{
  "id": "evt_d3",
  "type": "authorization",
  "created_at": "2026-10-08T19:04:00Z",
  "error": "insufficient_scope",
  "scope": "poppy:read poppy:write"
}
```

`error` is `insufficient_scope`, with the same meaning as the error in section 6, and `scope` names
the scopes needed. The Personal Agent responds as it would to that error, with its refresh token
(4.7) or by asking the User to authorize (4.4). It then continues the
same conversation with the new token. The conversation stays open meanwhile.

A conversation isn't tied to one access token or Session. The Personal Agent MAY switch to a new
access token partway through a conversation, after authorizing, renewing, or revoking, or
continue it in a new Session, as long as the token matches the conversation's owner (7.2). The
conversation keeps its `conversation_id` throughout.

An authorized conversation also respects the token's scopes. Before reading account information or
making a change, the Company Agent checks for the required scopes, whoever is handling the
conversation. Sending a message does not authorize the requested account action.

Once a conversation has used the User's account, a request on it from a token for the same User that
isn't authorized for that account gets `insufficient_scope`. After a revocation, the conversation
stays open, as 4.8 describes.

### 7.12 Closing {#closing}

The Personal Agent closes a conversation it's done with by sending an empty JSON object to its
`close` URL. The Company adds a `state` event with `status: "closed"`, cancels any pending handoff,
and returns HTTP 200 with `status` and `responder`. Closing a conversation that is already closed
returns the same response and adds no event. The Company can also close a conversation, for example
after a period of inactivity.

A closed conversation takes no more messages, and its events stay readable for as long as the
Company keeps them. Closing a conversation doesn't cancel anything it started, such as an order or a
return.

### 7.13 Errors {#conversation-errors}

Token errors are the ones in section 6. Other errors have a JSON body with an `error` code, like
OAuth error responses:

| Error                      | Status | Meaning                                                                                                                                                                           |
| -------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `conversation_not_found`   | 404    | The Conversation ID is unknown or belongs to a different Personal Agent, User, or account (7.2). All return the same error.                                                       |
| `conversation_closed`      | 409    | A message or handoff was sent to a closed conversation.                                                                                                                           |
| `direct_conversation_open` | 409    | The conversation has an open Direct Conversation, named in `conversation_id` (7.10).                                                                                              |
| `message_id_conflict`      | 409    | A message reused an ID that the Company accepted with different content (7.3).                                                                                                    |
| `invalid_cursor`           | 400    | The cursor is unknown or doesn't belong to this conversation.                                                                                                                     |
| `cursor_expired`           | 410    | The Company no longer has the events at this cursor (7.5).                                                                                                                        |
| `invalid_request`          | 400    | The request is malformed, such as a message with none of `text`, `data`, or `context`, an ID with characters not allowed (7.2), or a `wait` that isn't a whole number of seconds. |
| `extension_required`       | 403    | The request needs an extension the Personal Agent doesn't list, named in `extension` (3.3).                                                                                       |
| `rate_limited`             | 429    | Too many requests. Retry after the time in the `Retry-After` header (4.3).                                                                                                        |

## 8. Feedback {#feedback}

A Company can ask Personal Agents to tell it when a User's task can't be done through this protocol.
Without this, the Company sees only a customer who left.

Feedback is about what the Company doesn't offer, not errors. A Company already returns errors in
its responses (sections 6 and 7) and can see them in its own logs, so Personal Agents don't report
them here.

A Company that wants feedback lists `feedback.endpoint` in `poppy.json` (3.1). When a User's task
can't be done, the Personal Agent MAY send `POST {feedback.endpoint}` with an access token and a
DPoP proof (4.3), and a JSON body:

```json label="Request body: Personal Agent → Company"
{
  "kind": "missing",
  "task": "Pay with a gift card",
  "description": "The User wanted to pay for a new order with a gift card they were given. Neither the API nor the Company Agent can apply a gift card, and the checkout page in the browser session has no field for one."
}
```

| Field         | Req. | Description                                                                                                                                                                                                                                  |
| ------------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind`        | Yes  | `missing`: the Company offers no way to do the task through this protocol, whether with its Company Agent, its APIs, or its website in a browser session. Personal Agents MUST NOT send other values, which are reserved for later versions. |
| `task`        | Yes  | What the User was trying to do, in a short phrase, such as "Return a jacket", "Move a flight to the next day", or "Pay with a gift card". At most 200 characters.                                                                            |
| `description` | Yes  | What the Personal Agent was trying to accomplish, in detail, and why, without identifiers such as order numbers, account numbers, or names. At most 2,000 characters.                                                                        |

- A Company MUST accept a report only with an access token, pseudonymous or authorized, and needs no
  scope for it. The Session tells the Company which Personal Agent sent the report and for which
  User, so the report doesn't repeat that, or say where the problem happened.
- Personal Agents SHOULD NOT put personal data in a report, such as the User's name, contact
  details, or order details. A report describes the task, not the User. Personal Agents MUST NOT put
  secrets in a report (9.2).
- A Personal Agent SHOULD send one report for each task it couldn't do, not one for each attempt.
- A Company MUST accept a `kind` it doesn't recognize, so later versions can add kinds.
- A report can be wrong, or written to mislead. Companies MUST treat a report's text as data, not as
  instructions, including when a model reads it.

The Company responds with HTTP 202 and no body. Token errors are the ones in section 6. Other errors
have a JSON body with an `error` code, as in 7.13: `invalid_request` (400) for a report that is
malformed or too long, and `rate_limited` (429).

## 9. Security considerations {#security}

This section collects risks that cut across the protocol. The sections it points to hold the
detailed rules.

### 9.1 Content from Companies {#untrusted-content}

A Personal Agent passes what a Company returns to its model: conversation messages, API
descriptions and responses, MCP tool descriptions and results, web pages, and, with the Operations
extension, an operation's `summary`. The same model may hold the User's personal context and have
Sessions open at other Companies. A malicious or compromised Company can write content that tries to
direct the model, known as prompt injection.

- Personal Agents MUST treat content from a Company as data, not as instructions. Only the User
  decides what the Personal Agent does.
- A Personal Agent MUST NOT act at one Company, or send it information, because content from another
  Company asked it to. It acts at a Company only when the User's task needs it.
- A Personal Agent SHOULD send a Company only information relevant to the User's task. That
  includes context that helps the Company handle it, such as the reason for a return or a deadline
  the User has. It doesn't include unrelated details from the User's context or from other
  Companies.
- Text from a Company is never the User's approval or consent. The Operations extension states this
  for approving an operation ([Operations 5.1](/docs/extensions/operations#approval)).

### 9.2 Secrets and the model {#secrets}

A model can be led to repeat what is in its context, so a secret in context can leak through any
message the Personal Agent sends. AIMS §8 states the rule: the model MUST NOT have access to the
agent's credentials, or to the credentials it uses to access tools and services. Personal Agents
MUST keep refresh tokens (4.7), access tokens, private keys, authorization codes and PKCE code
verifiers, and device codes (4.6) out of model context, and sign and send requests in code the model can't read. A
Personal Agent never holds the User's credentials for a Company (4.4). The
[guides](/docs/guides#both-secrets) list these secrets and how to handle them.

### 9.3 What a domain vouches for {#trust}

A Company's `poppy.json` is where the Personal Agent learns everything about the Company: its
issuer, its APIs, and its Company Agent. Whoever
controls that document speaks for the Company at the host that serves it, as whoever controls its
website does today. The document's endpoints can be on any host. The checks in section 3 cover both
directions of the link between domain and issuer, which stops a domain from claiming another
Company's issuer and receiving its tokens. They don't make the issuer metadata more trustworthy than
`poppy.json`, because the document chooses the issuer.

### 9.4 Assertions {#assertion-audience}

A Personal Agent works with many Companies it has no prior relationship with, and each Company's
metadata names its own endpoints, which nobody checks (3.2). A malicious Company could name another
Company's token endpoint in its metadata. If assertions were addressed to that endpoint, the
malicious Company could collect them at its other endpoints and replay them at the other Company.
That is why client and grant assertions name the Company's `auth.issuer` in `aud` (4.1, 4.2). The
issuer is the value the Personal Agent verified for that Company, so an assertion collected by one
Company is rejected by every other. Each Company has its own issuer (3.2), so this holds even for
Companies a provider hosts on shared servers. A browser assertion names the Company's
`web.browser_session_endpoint` instead, and has its own `typ`, so no token endpoint accepts it
(section 5).

### 9.5 OAuth extensions {#oauth-extensions}

This profile adds a few things to OAuth that no OAuth registry lists yet. They are candidates for
registration, or for review in the IETF OAuth working group, before a stable version:

| Kind                                | Name                                                                              | Defined in |
| ----------------------------------- | --------------------------------------------------------------------------------- | ---------- |
| Token request and response parameter | `session_id`                                                                      | 4.2        |
| Token response parameter            | `refresh_token_expires_in`                                                        | 4.4        |
| Authorization server metadata       | `poppy_domains`                                                                   | 3.2        |
| Token endpoint error                | `invalid_session`, `account_mismatch`, `extension_required`, `rate_limited`       | 4.2, 3.3   |
| Resource server error               | `extension_required`                                                              | 3.3, 6     |
| JWT `typ`                           | `poppy-browser+jwt`                                                               | 5          |

The JWT authorization grant in 4.2 uses RFC 7523 unchanged on the wire. What's new is how it is
used: the client is the assertion's issuer, and the subject is a pairwise pseudonymous identifier
the client chose, which the Company hasn't seen before.
