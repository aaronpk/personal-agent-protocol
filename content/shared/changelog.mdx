# Changelog

What changed in each version of the specification, extensions, and guides, newest first. Each
published version stays at its own URL, such as [/docs/0.1/spec](/docs/0.1/spec).

## Draft 0.2 {#v0-2}

In progress, at [/docs/spec](/docs/spec). This list grows until 0.2 is published. Changes marked
"Breaking" can require an implementation that followed the 0.1 text to change.

- **A profile of AIMS.** The introduction frames the protocol as a narrow profile of the AI Identity
  Management System framework
  ([draft-ietf-wimse-aims](https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/)), and maps each
  AIMS component to the part of this protocol that profiles it ([1](/docs/spec#intro)).
- **OAuth terms.** The spec uses OAuth's names for what it profiles. Session Tokens are access
  tokens, Account Tokens are refresh tokens, and User IDs are pairwise subject identifiers. Signing
  in is user authorization through the authorization code grant, and signing out is revoking it. A
  Session is pseudonymous until the User authorizes it, and then authorized. The terms table says
  which OAuth role each party plays ([2](/docs/spec#terms)).
- **Breaking: HTTPS everywhere.** Every URL the protocol defines or exchanges is an HTTPS URL,
  including API and MCP URLs, metadata endpoints, and extension endpoints, which 0.1 didn't cover.
  Personal Agents don't use other URLs from a Company, and Companies reject them from a Personal
  Agent. Website pages a Personal Agent browses aren't covered ([3](/docs/spec#discovery)).
- **Breaking: Versions before 1.0.** Each 0.x version can break the one before, so a Personal Agent
  uses only a `poppy.json` whose `major.minor` version it supports. 0.1 promised that newer minor
  versions wouldn't break older Personal Agents, which 0.2 doesn't keep. That promise now starts at
  1.0 ([3.1](/docs/spec#fields)).
- **Breaking: Redirects and addresses.** Outside discovery, a Personal Agent doesn't send a token,
  DPoP Proof, assertion, or credentials to the URL a protocol endpoint redirects to. Neither side
  connects to loopback, private, or link-local addresses for URLs the other gave it, unless
  configured to ([3](/docs/spec#discovery)).
- **Breaking: Which domain `poppy.json` speaks for.** `organization.domain` is the host that serves
  the document after any redirects, not the host the Personal Agent requested. Domains are compared
  ignoring case only, so a leading `www.` is no longer ignored, and the `poppy_domains` check also
  ignores case. A Company that uses a provider has the provider serve the document on the Company's
  own domain ([3](/docs/spec#discovery), [3.1](/docs/spec#fields), [3.2](/docs/spec#oauth-server)).
  [Issue #5](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/5)
- **Breaking: One issuer per Company.** An issuer represents exactly one Company. A provider that
  hosts several Companies gives each its own issuer, even on shared servers, so they don't share
  User IDs or Account Tokens. The spec also says where the metadata is for an issuer with a path,
  as RFC 8414 defines ([3.2](/docs/spec#oauth-server), [4.2](/docs/spec#starting-sessions),
  [9.4](/docs/spec#assertion-audience)).
  [Issue #3](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/3)
- **Which Company a document speaks for.** Section 3 now explains in one place how `poppy.json` and
  the issuer's metadata confirm each other, and 3.2 lists `issuer` and `poppy_domains` among the
  metadata fields. The issuer is compared exactly and domains ignoring case. The redirect example
  now matches the example document. The rules themselves don't change ([3](/docs/spec#discovery),
  [3.2](/docs/spec#oauth-server), [9.3](/docs/spec#trust)).
- **Breaking: One `auth` per issuer.** Documents on several domains that name the same issuer have
  the same `auth`. Other fields can differ by domain ([3.2](/docs/spec#oauth-server)).
- **Breaking: Authorization support and scopes in the metadata.** `auth.direct`, `auth.device`, and
  `auth.mediated` are removed from `poppy.json`. A Company supports user authorization when its
  authorization server metadata lists `authorization_code` in `grant_types_supported` and has an
  `authorization_endpoint`, and it lists the scopes it can grant in `scopes_supported`. A Company
  that offers the device authorization grant lists it in `grant_types_supported` and gives the
  `device_authorization_endpoint`.
  `auth.custom_scopes` still describes the Company's own scopes ([3.1](/docs/spec#fields),
  [3.2](/docs/spec#oauth-server), [4.4](/docs/spec#sign-in)).
- **Breaking: More authorization server metadata.** The metadata includes `grant_types_supported`,
  `token_endpoint_auth_methods_supported` with `private_key_jwt`,
  `token_endpoint_auth_signing_alg_values_supported`, and
  `client_id_metadata_document_supported: true`. With the authorization code grant, it also
  includes `code_challenge_methods_supported` with `S256` and
  `authorization_response_iss_parameter_supported: true` ([3.2](/docs/spec#oauth-server)).
- **Breaking: DPoP algorithms.** Companies accept DPoP Proofs signed with `ES256`. They may list the
  algorithms they accept in `dpop_signing_alg_values_supported` in their OAuth metadata, and the
  list then includes `ES256`. A Company whose issuer serves other OAuth clients can leave the field
  out, since it tells them the issuer supports DPoP. Personal Agents sign with `ES256` or an
  algorithm from the list ([3.2](/docs/spec#oauth-server)).
  [Issue #12](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/12)
- **Breaking: `extension_required` responses.** At the token endpoint and at endpoints this protocol
  or an extension defines, the error is a JSON body. At APIs, it goes in the `WWW-Authenticate`
  header. It's listed in the token endpoint and API error tables. An MCP server returns it only to
  refuse the Personal Agent entirely, never for a single tool ([3.3](/docs/spec#extensions),
  [4.2](/docs/spec#starting-sessions), [6](/docs/spec#apis)).
- **Breaking: Assertion audience.** In 0.1, a client assertion's `aud` wasn't specified, and a
  Session assertion's was the Company's token endpoint. Both are now the Company's `auth.issuer`,
  and Companies reject any other `aud` ([4.1](/docs/spec#agent-identity),
  [4.2](/docs/spec#starting-sessions), [9.4](/docs/spec#assertion-audience)). [Issue
  #2](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/2)
- **User IDs for anonymous browsing.** A Personal Agent may give a User a new User ID for each
  anonymous browsing session, like a private browser window, and never signs in with it. Personal
  Agents must keep the mapping of each User's IDs across Companies confidential: no publishing it
  and no sharing it with third parties, other than service providers that process it for them
  ([4.2](/docs/spec#starting-sessions)).
  [Issue #11](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/11)
- **Breaking: Assertion lifetimes and replay.** A Session assertion's `exp` is at most five minutes
  after `iat`, and Companies reject a reused `jti` from the same `client_id` until it expires.
  Client assertions follow the same rules, and `aud` is compared character for character
  ([4.1](/docs/spec#agent-identity), [4.2](/docs/spec#starting-sessions)).
- **Breaking: No `signed_in`, and no empty `scope`.** Token responses no longer have `signed_in`. A
  pseudonymous access token's response leaves `scope` out, since an empty string isn't valid OAuth
  scope syntax, and an authorized one always includes `scope`, so the Personal Agent can tell them
  apart. The JWT authorization grant is described as the agent obtaining its own authorization, as
  AIMS §10.4.2 does ([4.2](/docs/spec#starting-sessions), [4.4](/docs/spec#sign-in)).
- **Breaking: A DPoP key per User ID.** Personal Agents use a different DPoP key pair for each User
  ID, so Companies can't link Users by their keys ([4.3](/docs/spec#sending-tokens)).
- **Breaking: DPoP Proof checks.** Companies MUST validate every proof as RFC 9449 §4.3 describes.
  That adds checks that the request has exactly one `DPoP` header, `typ` is `dpop+jwt`, `alg` is an
  asymmetric algorithm the Company accepts and never `none`, and `jwk` holds no private key. In 0.1,
  every endpoint had to reject a reused `jti`. Now only the token endpoint must, and APIs and
  conversation endpoints may. A Company can judge the acceptance window by when it issued the
  proof's `nonce`, not only by `iat`. Companies don't need to support `dpop_jkt`. Where the spec is
  silent, RFC 9449 applies ([4.3](/docs/spec#sending-tokens)).
- **Breaking: DPoP errors at APIs and conversations.** `invalid_dpop_proof` and `use_dpop_nonce`
  come with HTTP 401 and the `WWW-Authenticate: DPoP` header. At the token endpoint they're OAuth
  errors with HTTP 400 ([4.3](/docs/spec#sending-tokens), [6](/docs/spec#apis)).
- **Which requests carry a DPoP Proof.** Every request to the token endpoint and every request with
  a Session Token carries a proof, except a request for a Bearer token for an MCP server. Requests
  that carry neither, such as revocation, don't need one
  ([4.3](/docs/spec#sending-tokens)).
- **Breaking: DPoP at MCP servers.** An MCP server supports DPoP by listing
  `dpop_signing_alg_values_supported`, with `ES256`, in its protected resource metadata. The Company
  chooses the token type by the `resource` of the token request: a DPoP Session Token for such a
  server, never a Bearer one for a Personal Agent, and a Bearer token for any other MCP server, even
  if the request has a proof. Every token request for an MCP server, including one that starts a
  Session, includes `resource`. A Bearer token works only at the MCP server whose `url` is its
  `resource`, not at other paths on the same host. A server with DPoP still accepts Bearer tokens
  from MCP clients that don't implement this protocol, and rejects a DPoP token sent as a Bearer
  token. An MCP server's 401 has a challenge for each scheme it accepts, each with
  `resource_metadata`. New MCP servers should support DPoP ([4.3](/docs/spec#sending-tokens),
  [6](/docs/spec#apis)).
  [Issue #6](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/6)
- **`rate_limited` body.** At the token endpoint and at endpoints this protocol or an extension
  defines, such as conversations, the body is `{"error": "rate_limited"}`.
  APIs and the website keep their own bodies ([4.3](/docs/spec#sending-tokens)).
- **Breaking: A Session stays tied to its account.** Once a Session has been signed in to an
  account, it can only be signed in to that account again, even after sign-out. This applies to
  every sign-in type, and to using an Account Token with a signed-out Session
  ([4.4](/docs/spec#sign-in), [4.7](/docs/spec#account-tokens), [4.8](/docs/spec#sign-out)).
  [Issue #8](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/8)
- **Breaking: Mediated Sign-In removed.** Sending the User's credentials to the Company is the
  resource owner password credentials grant under another name, which RFC 9700 §2.4 says MUST NOT
  be used. Section 4.7 and `auth.mediated` are removed. Personal Agents MUST NOT collect a User's
  credentials for a Company or submit them, and Companies MUST NOT offer a way to submit them
  ([4.4](/docs/spec#sign-in)).
- **Breaking: Device authorization grant limited by RFC 10027.** Device Sign-In is now the device
  authorization grant, kept as an option for Personal Agents that can't use the authorization code
  grant. Companies that offer it and Personal Agents that use it MUST follow the cross-device best
  practices in RFC 10027 (BCP 247) §2. A Company assesses the risk, limits the scopes the grant can
  grant, and uses short-lived, single-use user codes, rate limits, and a consent page that says who
  started the request. A Personal Agent MUST NOT use the grant when it can use the authorization
  code grant. A new subsection explains why the grant is easier to use for phishing: anyone can
  start a request and send the User the link and code, and the User approves on the Company's real
  page. It adds requirements to reduce the risk, such as showing the code only in the conversation
  where the User asked for the task and warning the User about codes they didn't ask for
  ([4.4](/docs/spec#sign-in), [4.6](/docs/spec#device-sign-in)).
- **Phishing-resistant authentication.** Companies SHOULD offer a phishing-resistant way for the
  User to authenticate, such as a passkey, as AIMS §10.4.1 recommends
  ([4.5](/docs/spec#direct-sign-in)).
- **Renumbered.** Refresh tokens (formerly Account Tokens) move from 4.8 to 4.7, and revocation
  (formerly Signing out) moves from 4.9 to 4.8. Their links don't change
  ([4.7](/docs/spec#account-tokens), [4.8](/docs/spec#sign-out)).
- **Work after a token expires.** A Session Token expiring isn't a sign-out, and work the Company
  accepted with a valid token can continue. When access is revoked, the Company may stop work in
  progress that uses the account, or let it finish ([4.8](/docs/spec#sign-out)).
  [Issue #15](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/15)
- **Breaking: After revocation.** Section 4.8 gathers the rules for a Session that continues
  pseudonymous after the User revokes the authorization or disconnects the Personal Agent. What
  doesn't need the account carries on. Anything that used it, such as a conversation or an
  operation, stays as it is, and a pseudonymous token gets `insufficient_scope` on it. A
  conversation stays open, so the User can authorize again and continue it. The Personal Agent
  SHOULD NOT ask the User to authorize that account again unless the User asks, even when a request
  gets `insufficient_scope` ([4.8](/docs/spec#sign-out), [6](/docs/spec#apis),
  [7.11](/docs/spec#conversation-sign-in)).
- **Revocation invalidates access tokens.** As RFC 7009 §2.1 describes, a Company SHOULD invalidate
  the access tokens issued under a refresh token when it is revoked. Checking the Session on each
  request, or short access token lifetimes, remain the fallbacks ([4.8](/docs/spec#sign-out)).
- **Breaking: `sign_in_required` replaced by `insufficient_scope`.** A pseudonymous access token has
  no scopes, so a request that needs the User's account gets RFC 6750's `insufficient_scope`, with
  the scopes it needs. The same applies to the `authorization` conversation event
  ([6](/docs/spec#apis), [7.11](/docs/spec#conversation-sign-in)).
- **Sessions from plain MCP clients.** A Session started by an MCP client that doesn't implement
  this protocol has no User ID, can't continue signed out, and ends when its sign-in does
  ([6](/docs/spec#apis)).
- **Conversation query parameters.** `cursor` and `wait` are query parameters, as the 0.1 examples
  showed, on reads and on the `POST` requests that send a message or hand off. `wait` is a whole
  number of seconds ([7.3](/docs/spec#sending-messages), [7.5](/docs/spec#reading-events)).
- **Breaking: Messages.** `role` is listed as a message field, set by the Company. A `message` event
  holds the message as it was sent, and every accepted message is recorded, including one with only
  `context` ([7.4](/docs/spec#message-fields), [7.5](/docs/spec#reading-events)).
- **Long polling.** A Company that caps `wait` holds the request for its cap instead of rejecting it
  ([7.5](/docs/spec#reading-events)).
- **Breaking: Read fields.** Every successful read includes `conversation_id` and `events`, as the
  examples showed, along with `cursor`, `has_more`, `status`, and `responder`. `events` is empty
  when there are none ([7.5](/docs/spec#reading-events)). [Issue
  #13](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/13)
- **Streaming.** When a request has both `Last-Event-ID` and `cursor`, `Last-Event-ID` wins
  ([7.6](/docs/spec#streaming)).
- **Repeated requests.** Handing off a conversation that is already queued or with a person, or
  closing one that is already closed, returns the current state and changes nothing
  ([7.9](/docs/spec#handoff), [7.12](/docs/spec#closing)).
- **`user_requested`.** The event doesn't change `status` or `responder`
  ([7.10](/docs/spec#direct-conversations)).
- **Conversation errors.** Conversations add `invalid_request` (400) and `rate_limited` (429)
  ([7.13](/docs/spec#conversation-errors)).
- **Feedback.** A new section 8 lets a Company list a `feedback.endpoint` in `poppy.json`. With a
  Session Token, Personal Agents can report a User's task that the Company offers no way to do
  through this protocol. A report has a `kind`, which is `missing` for now, the `task`, and a
  `description` without identifiers, and isn't for errors ([3.1](/docs/spec#fields),
  [8](/docs/spec#feedback)).
  [Issue #9](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/9)
- **Breaking: Security considerations.** A new section 9 covers content from Companies and prompt
  injection, secrets and the model, what a domain vouches for, and why assertions name the issuer.
  It adds requirements for Personal Agents: they MUST treat content from a Company as data, not
  instructions, and MUST NOT act at one Company, or send it information, because another Company's
  content asked. References move to section 10 ([9](/docs/spec#security),
  [9.1](/docs/spec#untrusted-content)). [Issue
  #4](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/4)
- **Browser assertion audience.** Section 9.4 now says that client and Session assertions name the
  issuer, and that a browser assertion names the browser session endpoint and has its own `typ`
  ([9.4](/docs/spec#assertion-audience)).
- **Breaking: Secrets out of model context.** Following AIMS §8, Personal Agents MUST keep refresh
  tokens, access tokens, private keys, authorization codes, PKCE code verifiers, and device codes out
  of model context. Before, only Account Tokens were a MUST ([9.2](/docs/spec#secrets)).
- **OAuth extensions.** A new section 9.5 lists what the protocol adds to OAuth that no registry
  lists yet: `session_id`, `refresh_token_expires_in`, `poppy_domains`, its error codes, and the
  `poppy-browser+jwt` type. Section 10 adds AIMS, RFC 9700, RFC 10027, and CIBA
  ([9.5](/docs/spec#oauth-extensions), [10](/docs/spec#references)).
- **`extension_required` in conversations and Operations.** The conversation error table lists
  `extension_required`. An MCP tool that needs the Operations extension returns an ordinary tool
  error, since an MCP server can't refuse a single tool call with `extension_required`. The
  Operations error table lists `rate_limited` and no longer lists `extension_required`
  ([7.13](/docs/spec#conversation-errors), [Operations 2](/docs/extensions/operations#support),
  [Operations 9](/docs/extensions/operations#errors)).
- **Breaking: Operations after revocation.** An operation proposed in an authorized Session can be
  used only by a Session that is authorized for the same account at the time of the request,
  including the original one. A pseudonymous Session of the same Personal Agent and User gets
  `insufficient_scope` ([Operations 3.2](/docs/extensions/operations#ownership)).
- **Operations.** Personal Agents should show the User the values in an operation's `terms` next to
  its `summary`, or check that they agree, before asking for approval ([Operations
  5.1](/docs/extensions/operations#approval)). [Issue
  #4](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/4)
- **Examples.** The request that waits for a reply is shown in full, the API write examples include
  an `Idempotency-Key`, the example DPoP Proof's `jti` has 128 random bits, and the Operations
  conversation example has its own event ID ([7.3](/docs/spec#sending-messages),
  [Operations 4.3](/docs/extensions/operations#binding-conversations)).
- **Guides.** Sign DPoP Proofs with ES256, which every company accepts. A company's token endpoint
  keeps a replay cache shared by every server, and its APIs may keep one too. A client or Session
  assertion's `aud` is the company's `auth.issuer` ([Guides](/docs/guides)). [Issue
  #5](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/5)
- **Guides: key refetches, rate limits, and running work.** Companies refetch a personal agent's
  keys at most once per interval, counting failures, and charge per-agent rate limits only after the
  signature checks pass. Accepted work isn't stopped because a session token expired, and work that
  can take consequential actions stops right away when access is revoked
  ([Rotating keys](/docs/guides#both-key-rotation), [Rate limits](/docs/guides#both-rate-limits),
  [Token lifetimes and sign-out](/docs/guides#company-lifetimes)).
  [Issue #15](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/15)
- **Guides: hosting several companies.** A new section for providers that host several companies,
  with an example of which storefronts share an issuer, metadata for an issuer with a path, and
  keeping each company's tokens and records apart on shared servers. Personal agents key user IDs
  and account tokens by the full `auth.issuer` ([Hosting several
  companies](/docs/guides#company-hosting), [User IDs](/docs/guides#agent-user-ids)).
  [Issue #3](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/3)
- **Guides: conversations after sign-out.** Companies can leave conversations that used the
  account open after sign-out, answering pseudonymous tokens with `insufficient_scope`, instead of
  closing them ([Conversations](/docs/guides#company-conversations)).
- **Guides: user ID privacy.** Personal agents tell users that companies recognize them across
  signed-out visits and that signing in links those visits to their account. A new list covers
  anonymous browsing: a new user ID and DPoP key for each session, discarded when it ends ([User
  IDs](/docs/guides#agent-user-ids)).
  [Issue #11](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/11)
- **Guides: finding a company.** When the company a personal agent reaches is on a different domain
  from the one the user asked for, it tells the user which company it's dealing with before signing
  in or acting for them ([Finding a company](/docs/guides#agent-discovery)).
- **Guides: matching the spec.** Personal agents sign assertions and proofs with ES256, and don't
  send a token or proof to the URL a protocol endpoint redirects to. Without a browser session
  endpoint, personal agents
  browse only as signed-out visitors. The token endpoint's replay rule and `iss` in Direct Sign-In
  redirects cite the spec without overstating it ([Guides](/docs/guides)).
- **Guides: sign-in without passwords, and device codes as a last resort.** The guides for
  Mediated Sign-In are removed. Personal agents send the authorization URL to the user when they
  can't receive the redirect on the user's device, use the device authorization grant only when
  they can't do that, and never type the user's password into a company's website. Companies offer
  a passkey, apply RFC 10027's cross-device mitigations on their consent page, and offer the device
  authorization grant only with the mitigations RFC 10027 calls for ([Choosing how to sign
  in](/docs/guides#agent-choosing-sign-in), [Device authorization
  grant](/docs/guides#agent-device), [Consent pages](/docs/guides#company-consent)).
